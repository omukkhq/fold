# fold reference

This file sits next to the `fold` skill and holds the formats and commands around the workflow: the checks file, the project config, area profiles, ignore files, the human's `fld` commands, the web app and an index of the fold tools. Read the section you need before you plan checks, change config, define areas or tell the user what to run. `fld init --refresh` writes this file again when it is missing.

## Checks

`fold-checks.toml` at the root of the project's tree names the commands that must pass before work reaches main. Each tree's own copy decides, so a proposal changes its checks together with its code. A project without the file has no fold checks.

```toml
# Runs before the checks of every run, in the directory where they run.
[setup]
run = "bun install --frozen-lockfile"

[[check]]
name = "rust-tests"
run = "cargo test --workspace"
files = '\.rs$|(^|/)Cargo\.(toml|lock)$'
# At most one run of the project runs this heavy suite at a time.
max_parallel = 1

[[check]]
name = "web"
run = "cd web && bun run test"
files = '^web/'

[[check]]
name = "lint"
run = "cargo clippy --workspace -- -D warnings"
required = false
timeout = "10m"

[[check]]
name = "acceptance"
run = "make acceptance"
stage = "integration"
timeout = "2h"

[[check]]
name = "build"
run = "cargo build --workspace"
stage = ["proposal", "integration"]

# Proposals that change these paths integrate one at a time.
[[serial]]
name = "migrations"
paths = ["crates/store/migrations/**", "Cargo.lock"]
```

Keys. Every key is known, and a misspelt key refuses the whole file with `checks_file_invalid`, whose message names the line or the check:

- `[setup]` with `run`: one shell command that runs first in every run, such as installing dependencies. A failed setup fails the run with `setup_failed`, and no check runs (`not_run`). fold also runs it in the background in each task workspace that `create_workspace` makes or adopts and in each review checkout that `create_review_checkout` makes, from that folder's own `fold-checks.toml`: the tool answers `setup` `running` (or `none` without a setup), a message from fold reports the end (passed, or the end of the failed log), and a check run of the folder waits until the setup ends.
- `[[check]]`, at most 64, each with:
  - `name`: 1 to 64 letters, digits, `_`, `-` or `.`, unique in the file.
  - `run`: the shell command, at most 4000 characters. It runs as `sh -c` in the check directory, with stdin closed and without fold's agent and human variables. A fold call from inside a check acts only as the agent of the worker that asked for the run, never as a human.
  - `files`: optional. A regular expression, not a glob, searched anywhere in each changed path; `'^web/'` matches the folder `web` at the root and `'\.rs$'` every Rust file. A check whose pattern matches no changed path is `skipped`. Without it the check always runs.
  - `required`: optional, `true` by default. A check with `required = false` shows its result and never blocks.
  - `stage`: optional, `proposal` (the default), `integration`, or a list such as `["proposal", "integration"]` to run the check in both stages under one name. A string is a list of one. An empty list, an unknown name or a repeated name refuses the file.
  - `timeout`: optional, a whole number with `s`, `m` or `h`, such as `"90s"`, `"10m"` or `"2h"`, from 1s to 24h. The default is 30 minutes. fold stops a command's whole process group at its timeout (`timed_out`), and at its end, so a server that a test started ends with it.
  - `max_parallel`: optional, a whole number of 1 or more. At most this many runs of the project run the check's command at the same time, in the proposal and the integration stage together. Another run waits before the command, holding its place among the machine's runs, and goes on when one of them ends it; its earlier commands, and the checks of other runs, are not held. The wait counts in neither the check's duration nor its timeout. `0`, a string or a fraction refuses the file. Without it the check has no limit of its own. Use it for a heavy suite, such as `pytest -n 8`, so its runs do not fill the memory while light checks such as format and lint run as before.

- [runs] with max_parallel_runs: optional, a whole number of 1 or more, such as max_parallel_runs = 2 under a [runs] line. At most this many check runs of the project run at the same time. A run over the limit waits in the order it was asked for, before the memory wait, and starts when a run ends and frees its place; `checks.started`, `get_check_run` and `get_proposal` show it with `waiting_for` run_slot and its `position`, 1 for the next run. A waiting run keeps the claims of its worker as a running one does. An integration run counts against the limit but never waits for it. Without the key, nothing limits the runs of the project.
- [runs] with build_slot_wait: optional, a duration in the form of a check's `timeout`, such as build_slot_wait = "3h", from 1s to 24h; the default is 2 hours. It is how long one command may wait for a slot of the machine's build gate (scripts/build-gate.sh). The gate writes the line "build-gate: slot taken" on stderr when it takes a slot, and the command's timeout counts only from that line; a command that never writes it keeps its timeout from its start. While the gate writes that every slot is in use, `get_check_run` and `get_proposal` show the run with `waiting_for` `build_slot` and the time it began to wait. A command that waits longer than build_slot_wait is stopped and the run fails with reason `no_build_slot`.
- `[[serial]]`, at most 16, each an integration lane with:
  - `name`: 1 to 64 letters, digits, `_`, `-` or `.`, unique among the lanes.
  - `paths`: 1 to 64 globs of 1 to 500 characters each, relative to the root without empty, `.` or `..` segments. `*` and `?` match inside one segment, and `**`, only as a whole segment, matches any number of segments. A path that matches the globs of several lanes belongs to the first of them in the file.
  - `refresh`, optional: one line of 1 to 1000 characters without control characters that names the step to redo on the new main, such as "put the migration on the current head". When main changed a path of the lane since a member's version base, fold starts no integration run for that member: it sends the version to the reviewer that approved it the way it sends a conflict, with this text, and the reviewer's fix version runs its checks. `get_proposal` names the lane's refresh as the reason the version waits. A member whose base holds main's lane paths integrates without a refresh, and a lane without the key only orders its members.

The file is at most 256 KiB. Prefer one check per tool or part of the repository with a `files` pattern, so a change of the docs runs no test suite.

Stages:

- `proposal` checks run on the files of a version before fold makes it. A task worker asks with `run_checks(task)`; `create_proposal` and `update_proposal` run them when no passed run of the same files on the same base stands, and answer with `checks` `running` and a run id; a reviewer's `submit_review_fix` runs them in its review checkout. They run in the author's task workspace or the reviewer's checkout, and the changed paths are those of the change against the workspace's base. A version comes into being only when the required checks pass. A human's edit in the web app, `fld record` and `submit_main_change` run no proposal checks.
- `integration` checks run on the merged tree, after the approvals and before fold publishes the revision, under the project's integration lock, so main cannot move meanwhile. They run in `.fold/checks/main`, fold's own copy of main that keeps what the setup installs between runs and follows main after every revision. Only the integration checks whose pattern matches a path the merge changes on main run. A failure publishes nothing and sends the proposal back to its author, whose task worker fold resumes, except a lane failure as Queue and load says. A conflict of the merge goes to the reviewer that approved the version, never to the author. `submit_main_change` runs them on the merge of its changeset in the same way, as a run that names the changeset: a failure publishes nothing, answers `checks_failed` with the run, sends the main agent a message and leaves the main workspace open for the fix. `fld record` runs no integration checks.

Runs and results. A run is `running`, then `passed`, `failed` or `stopped`; each command is `passed`, `failed`, `timed_out`, `skipped` or `not_run`. A failed or stopped run names its reason: `check_failed`, `setup_failed`, `checks_file_invalid`, `files_changed` (a check or an edit changed the recorded files during the run: in a task workspace fold stops the run at the first scan that finds the edit and names the path in `checks.finished` and in its message, so do not edit until `checks.finished` and put what a check writes in `.gitignore`), `workspace_changed`, `refused` (the command the run waited for is refused now), `daemon_stopped`, `superseded` (an integration started again on a newer state), `fold_failed` (fold itself could not run the checks; the run says nothing of the change, and the proposal keeps its version and approvals), `killed` (a signal fold did not send ended a command; no later command starts. Mostly the kernel's OOM killer ended it when the machine ran out of memory; its log ends with "killed: out of memory or by a signal", the command is `failed`, and the run says nothing of the change, so run the checks again once memory is free), `no_build_slot` (a command waited longer than build_slot_wait for a build gate slot; no later command starts, the command is `timed_out`, and the run says nothing of the change, so run the checks again when the machine is less busy) or `cancelled` (someone cancelled the run with `cancel_check_run`). On Linux every check command starts with an OOM score adjustment (oom_score_adj) of 800, which its processes inherit, so the kernel ends a check before the daemon or a worker. fold sends the result as a message from fold to the worker that asked, with the failed checks and the end of the first failed log; `get_check_run(run)` lists only the failed commands, each with the last 60 lines or 3000 characters of its log, and counts the others in `not_shown`; with `detail` `full` it lists every command with the last 200 lines or 20000 characters of its log; and `get_proposal` lists the runs of a version in `checks`. A failed or timed-out check is flaky when a later run of the same tree passes the same check; the setup is never flaky. `get_check_run` and the run views mark each such result with `flaky`, and `list_flaky_checks(days?)` lists the project's flaky checks of the last `days` days (14 when left out, at most 365) by the number of flaky failures, then by name, with the failed runs. The events are `checks.started`, `checks.finished` and `checks.flaky`, which names the earlier failed `run`, the `passed_run` and the flaky `checks` once for each earlier run.

Queue and load. One run at a time goes in a workspace; a second gets `checks_running`. Integrations of a project wait in a queue in the order they were asked for. An open proposal whose current version changes a path of a `[[serial]]` lane of main's file is a member of that lane. The members of a lane integrate one at a time, in the order of their first approval on any version, then by proposal number; a member without an approval waits behind every approved one. Only the front member integrates: `integrate_proposal` refuses another with `invalid_request`, the reason `lane_held` and its `lane` and `position`, and automatic and batch integrations wait the same way. `get_proposal`, `list_proposals` and `list_workers` show each member's lane and position. When a member conflicts or fails its integration checks after main changed a lane path since its version's base, the failure goes to the reviewer that approved the version, with a note that the lane moved. fold runs the queue and the lanes itself; no agent orders, holds or retries them by hand. An approved proposal whose `queue` field shows a `position` needs no action, and `integrate_proposal` would move it ahead of older approvals; call it by hand only when `waits_for` shows a `reason` that needs a person, such as an integration that is off, or when a human asks. All projects of the daemon share at most half the processors' worth of check runs at once. A run that has its place starts its commands only while the machine's free memory (`MemAvailable` of `/proc/meminfo`) is at or above the larger of 4 GiB and 10% of the total memory; until then it waits, reads the memory again every 10 seconds, and `get_check_run`, `get_proposal` and the run views show it with `waiting_for` `memory` and the time it began to wait. Systems without `/proc/meminfo` skip the memory check. A run that waits before the command of a check with `max_parallel` shows with `waiting_for` `check`, the check's name in `waiting_check` and the time it began to wait.

Changing the checks. A proposal version that adds, changes or removes `fold-checks.toml` gives its task the human review mark when it has none, so a human approves every change of the checks and no agent can weaken one without the user. Write the first file as a task of the area `main` or as a main workspace change with the user's OK (`submit_main_change`, where that OK is the approval). When main's own file is not valid, fold holds every integration, sends `integration.held` and lists the problem in Needs you under Project; a revision of main that fixes it, from `submit_main_change`, `fld record` or a proposal that fixes the file, lets the held integrations go on. `submit_main_change` is never held: while main's file is not valid, its run fails with `checks_file_invalid` unless the change fixes the file.

## Project config

`.fold/config.toml` holds the project's settings. `fld init` writes it with every value commented out at its default. It is outside the project's tree, so agents never edit it: tell the user the exact lines to change. `set_worker_limits` rewrites only `[workers]`. fold reads the file when it uses a value, so most edits apply at once; the watcher reads `debounce_ms`, `rescan_seconds` and `max_file_bytes` when the daemon opens the project, so an edit of them reaches it after `fld restart`. The bullet "How fold follows workspace changes" below describes the watcher. An invalid file fails the commands that read it with `invalid_config`, which names the key. The top-level key `deny_commands` holds the Claude Code Bash rules that every worker of the project gets as `permissions.deny`, such as `deny_commands = ["Bash(psql:*)"]`; an area's `deny_commands` add to it, with the same checks.

```toml
lease_minutes = 30                   # a claim expires after this long without a heartbeat
debounce_ms = 500                    # the watcher waits this long after a file change before it scans
rescan_seconds = 60                  # time between full scans of a workspace, the base of how fold follows changes
auto_checkpoint_quiet_seconds = 120  # quiet time before an automatic checkpoint
auto_checkpoints_kept = 20           # automatic checkpoints each workspace keeps
max_file_bytes = 52428800            # a larger file keeps its recorded version and gives a warning
stall_minutes = 5                    # a worker that fold runs counts as stalled after this long with no open tool call and no output; a session fold does not run, after this long without a file change; never while its workspace runs checks or its worker waits for a person's answer, and counted from the end of its last run, a person's answer or a worker start
closed_workspace_days = 14           # how long `fld gc` keeps the checkpoints of a closed workspace, a record only; also how long a closed workspace's directory waits for its owner, and a finished worker's folder stays; at least 1, since fold refuses 0, so an owner that still runs keeps a closed directory for at least a day
request_escalate_minutes = 10        # a new request in an area goes first to that area's lead; after this long without a claim, fold tells the main agent and every area lead of it
account = "work-a"                   # optional: the host account whose Claude subscription the project's workers and main agent use; `fld account use` writes it, and without it they use default, Claude Code's own login

[git]
branch = "main"                      # the branch of the project folder's .git that every integration commits to

[remotes.origin]                     # one section per remote; `fld remote add` writes it
url = "git@example.com:team/app.git"
branch = "main"
push_on_integrate = false            # true pushes main to this remote after every integration

[integration]
automatic = true                     # false: an agent that decides reviews, or a human, integrates each ready proposal

[workers]
task_worker = 4                      # task workers running at once
reviewer = 3                         # reviewers running at once
max_per_area = 2                     # optional: task workers of one area at once

[main]
supervised = false                   # true: fold runs the main agent as a supervised worker of role main, for a server where nobody runs `fld claude`

[roles.task_worker]                  # also area_lead, review_lead, reviewer and main
model = "sonnet"                     # passed to Claude Code as --model
cache_ttl = "5m"                     # "1h" or "5m": "1h" for leads and "5m" for reviewers and task workers by default
idle_minutes = 15                    # task_worker and reviewer only: an idle worker stops after this long
mcp = ["fold", "pencil"]             # the servers the role may load: fold and servers of the project's .mcp.json

[roles.review_lead]
handoff_at = 50                      # area_lead, review_lead and main only: the percent of the context window past which fold refreshes the lead through a hand-off note; without it, 40% for the review lead, and for the others 85% of the window below 220k tokens and 60% from 220k
```

- The top-level numbers must be whole numbers above 0. A worker limit has no upper bound, and 0 lets no worker of its role start; the leads are outside the limits, and a lower limit never stops a running worker.
- `automatic = true` integrates a proposal once a reviewer, the main agent or a human approved it, nothing asks for changes, a human approved it when the task is marked, and every prerequisite task is Done.
- A role without `mcp` loads every server the user's own Claude Code loads. With `mcp`, the worker gets the fold server and each named server of the project's `.mcp.json`; servers of the user's own configuration are never copied.
- How fold follows workspace changes: every workspace gets a full scan every `rescan_seconds`, so it is correct within that time with no watch. On Linux, a workspace whose worker works or waits in an open session also gets its own inotify watch, with one instance and one kernel queue for each workspace and no open events, so reads cause no event; after `debounce_ms` of quiet a change is scanned. The workspaces of stopped workers have no watch and use the timer scan alone. When the daemon opens a project, it gives the workspaces their watch 4 at a time, 2 seconds apart. A workspace that loses notifications (the kernel queue of `fs.inotify.max_queued_events` overflowed) is scanned in full once; at 3 losses within 60 seconds it goes to timer mode for 10 minutes, and a workspace for which the system refuses an inotify instance stays in timer mode. In timer mode fold scans the workspace every 10 seconds. Fold then appends `workspace.watch_degraded` with `data.reason` `overflow` or `instance_limit` (other reasons are `watch_limit` and `no_native_watcher`), and the workspace list shows its `watch` as `degraded`. After the 10 minutes of an overflow fold watches the workspace again and appends `workspace.watch_restored`. The group size, the gap and these limits have no config key; `debounce_ms` and `rescan_seconds` are the only keys. `fld doctor` warns when `fs.inotify.max_queued_events` is below 16384 or `fs.inotify.max_user_instances` is below the number of watched workspaces plus a margin of 64, gives the `sysctl` line, and names the workspaces in timer mode; fold works without a change of those limits, and a change only makes changes show sooner.
- An older file with `remote` and `push_on_integrate` in `[git]` is read as `[remotes.origin]` on the `[git]` branch.
- `supervised = true` under `[main]` makes fold run the main agent itself: it starts it at the daemon's start, keeps its session, and resumes it for a message to it, a request, a ready task of `main` or a review it must act on, never while the project is paused. The humans talk to it in the web app, and `fld claude` refuses with `main_supervised`. While a `fld claude` session is the main agent, fold starts no supervised one (`main_interactive`), and once that session ends fold starts it. A human's Stop on the Agents screen holds the supervised main: fold starts it for no work until a human starts it in a new session.

Role prompts. `.fold/roles/<role>.md` (`area_lead`, `review_lead`, `task_worker` or `reviewer`) replaces the prompt that ships with fold for that role, and `.fold/roles/main.md` replaces the main agent's; fold adds its shared authority and recovery rules after either. For the supervised main, fold first adds its rules of a main agent without a terminal after `.fold/roles/main.md`. A worker gets a changed prompt at its next start.

## Areas

An area is a part of the project that one area lead owns, with one label that every task of the area carries. Make the label with `create_label`, then `define_area(name, label, instructions?, model?, mcp?, deny_commands?)`; change it with `update_area(name, instructions?, model?, mcp?, deny_commands?, clear_instructions?, clear_model?, clear_mcp?, clear_deny_commands?)`. The profile:

- `instructions`: at most 8000 characters, added to the system prompt of the area's lead and task workers under `## Area <name>`. Name the folders the area owns and what matters for its work. They specialize work inside the role and never widen its rights or the approved scope.
- `model`: a Claude Code model name or alias without spaces, such as `opus` or `sonnet`.
- `mcp`: a list of distinct server names, never empty. The fold server is always there, and `["fold"]` gives the workers no other server.
- `deny_commands`: a list of distinct Claude Code Bash rules, never empty, such as `["Bash(psql:*)", "Bash(docker exec:*)"]`, for shell commands the area's workers may never run, such as commands that reach a production database. fold writes them as `permissions.deny` into the Claude Code settings of the area's lead, its task workers and the reviewers of its proposals, after the top-level `deny_commands` of `.fold/config.toml`, each rule once. Each rule is `Bash(<command>)` of at most 200 characters whose command word has no `*`; a rule for another tool, a rule that denies every command, `cd` or `fld`, which fold's own work needs, and a rule named twice are refused with `invalid_permission_rule`, the rule in `details.rule`. Claude Code checks each part of a compound command such as `cd '<workspace>' && psql ...` against the rules, so a prefix rule still applies there. A rule is not a security boundary: Claude Code does not unwrap a wrapper such as `docker exec` or `sh -c`, so list each wrapper that reaches the same program as a rule of its own, such as `Bash(docker exec:*)`.

A field left out falls back to `[roles.<role>]` of `.fold/config.toml`, and the `model` and `instructions` of a `start_worker` call come before the profile. A reviewer takes only the `deny_commands` of each area whose tasks its proposals are for, in area-name order. fold writes the prompt and the settings at each start and resume, so a changed profile reaches the next start or resume and never a running worker.

```text
create_label(name: "design")
define_area(name: "design", label: "design",
  instructions: "You own the screens in design/. Draw each screen in Pencil; change no code.",
  model: "opus", mcp: ["fold", "pencil"])
```

The built-in area `main` with the label `main` holds the tasks only the main agent builds, such as `fold-checks.toml`, the root `.gitignore` or the notes in `AGENTS.md` before code lands. It has no lead and no profile: `define_area` refuses its name and label with `area_exists`, and `start_worker` and `update_area` refuse it with `main_area`. Each of its tasks gets the human review mark unless the approved plan gives it `main_approves`. When a task leaves `main`, fold takes off the mark it set there, and a mark a person set stays.

## Task descriptions

A task description has a summary paragraph, then **Refs**, **Scope**, **Out of scope** and **Acceptance**, as the task template of the planning steps says. The optional **Decisions** section always comes last. It holds the decisions that a person gave after the task was written, such as in the main agent's conversation, in a reply to an ask or in a request thread. The agent that gets a decision calls `update_task` at once: it changes the affected Scope or Acceptance text, so the description never says the old value, and appends one entry, newest last:

```markdown
**Decisions**:
- 2026-11-22 (UTC): the cache holds 80k entries. By: @ana. Source: #m-210. Replaces: 40k entries.
- 2026-11-23 (UTC): the export also writes CSV. By: @ana. Source: the main agent's conversation. Replaces: JSON only.
```

Each entry gives the date (UTC), the decision, who gave it, the source (`#m-<id>`, or "the main agent's conversation") and what it replaces. A decision inside a request that is still drafting goes into the cards of the next draft version instead. A decision that changes Done work is recorded on the Done task, which stays Done, and a new task for the change names the decision and the Done task with `#T-<id>`.

Every agent reads the `Decisions` section before the older description text and before the request text, and a newer decision before an older one. When the code, the description or the request disagree and no decision settles it, the agent asks the humans and never picks the older value.

## Ignore files

- `.gitignore` and `.foldignore` are files of the tree, in any folder, in the format of Git's ignore files. As in Git, they apply only to paths the tree does not track yet: fold never starts to track, record or propose a path they ignore, but a tracked file stays tracked when a rule matches it, so its changes and its deletion are recorded. A tracked file leaves main only when a change deletes it, or when the user runs `fld untrack <path>`, which removes it from main and leaves it on disk. Each applies below its own folder; a `.foldignore` rule wins over a `.gitignore` rule, so a `.foldignore` can ignore more for fold alone or bring a path back with `!`. `fld init` writes an empty `.foldignore` when the folder has none.
- `.fold/exclude` holds paths that stay out of fold and Git on this machine only, such as local notes or tool output; it is never part of the tree. `.git/info/exclude` is a link to it, so Git and fold leave out the same paths, and it always lists `/.fold/`. The user edits it, or `add_exclude_patterns(patterns)` adds `.gitignore` lines when the user asks. A `!` line of `.gitignore` or `.foldignore` brings an excluded path back.
- `.fold/shared` lists ignored files and folders that workers read, such as design files: one path relative to the project folder per line, below fold's comment line; like `.fold/exclude` it belongs to this machine and is never part of the tree. `fld share <path>...`, `fld unshare <path>...` and `share_paths(paths)` of the main agent change it (an unshare also removes the `.fold/exclude` line that its share added, never a line of the user's), and `fld share --list` shows it. A shared path must be in the project folder, reached without a symbolic link, left out by an ignore rule, and neither within nor around another shared path; fold never shares an ignored file by default, because many are secrets. A folder that only a folder pattern such as `design/` leaves out also gets the line `/design` in `.fold/exclude`, so its link is never recorded. Every task workspace and review checkout, and fold's folder for integration checks, gets one symbolic link per shared path, at the same path, to the absolute path in the project folder, at its create and its sync, the points where fold writes into a workspace; a sync also removes the link of a path no longer shared. A path where the workspace holds something else gets no link. The links are ignored, so they are never recorded, proposed or counted as changes, and checks can read them. Workers only read them: `fld hook pre-tool-use` resolves real paths, so an edit through a link, or a shell command started in a linked folder, is refused like one in the project folder. `get_task` names the shared paths in `shared`. `fld status`, `fld share --list` and the web app's repository screen name the ignored paths no worker sees, the first ten and a count.
- fold starts every worker but the main agent in its own start folder, `.fold/workers/<name>/start`, and the worker's shell goes back there after each command (`CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR`), so a relative path of a shell command without `..` never lands in the project folder. The start folder lies inside the project folder, so a path with `..`, or a command that changes into the project folder, still reaches it and fold's data. At each start fold makes the start folder again, which removes what the worker left there, and copies the project's `.claude/settings.json`, `.claude/settings.local.json` and its own skills into it, so the worker reads the same settings and skills; a hook command that names `$CLAUDE_PROJECT_DIR` gets the project folder's path in the copy, because Claude Code sets the variable to the start folder. The project's `.mcp.json` is not copied, because a `-p` session connects every server of its folder's `.mcp.json`, approved or not: the worker's MCP configuration holds the servers the user approved for the project folder in Claude Code (`enableAllProjectMcpServers`, or `enabledMcpjsonServers` without `disabledMcpjsonServers`, in `~/.claude.json`, the user settings or `.claude/settings.local.json`) and the servers you added for the project folder alone (`claude mcp add` without `--scope`, kept in the folder's entry of `~/.claude.json`), or, for a role with an `mcp` list, the servers that list names. That configuration, `.fold/workers/<name>/mcp.json`, can hold the credentials of those servers, so fold writes it readable by you only. A `-p` session never applies the `permissions.allow` rules of a folder the user did not trust, so when the user trusted the project folder fold passes those rules of `.claude/settings.json` with the worker's own settings. The workspaces in `.fold/ws/` are the worker's other working folder (`--add-dir`). `fld hook pre-tool-use` refuses a worker's shell command that would start in the project folder outside `.fold/ws/`, unless the command starts with `cd` into a workspace followed by `&&`; it checks where a command starts, and refuses a command that names a shared path as a write target in a common form: `>` and `>>` redirects, `tee`, `cp`, `mv`, `rm`, `ln`, `touch`, `truncate`, `install`, `sed -i` and `dd of=`. That is a net for common mistakes, not a boundary: a script or an interpreter writes where its text does not say. Checks also see the shared paths through links in fold's check folder, and a check command that writes there changes the project folder with no guard and no Needs you item. fold also notes the size, modification time and, for a small file, the content hash of each shared file (at most 2000), reads them again every second, and when one changed during a supervised worker's tool call, Needs you shows "@agent changed a shared file while it worked" with the files (`shared_changed`), until the user checks them and chooses Dismiss or runs `fld share --dismiss`. A change outside every tool call, such as the user's or the main agent's edit, only moves what fold noted. Only Claude Code's sandbox refuses every write outside the working folders; to turn it on for the workers too, set `"sandbox": {"enabled": true}` in `~/.claude/settings.json` (on Linux it needs `bubblewrap` and `socat`, and it limits the network of shell commands to the hosts you allow). Claude Code keeps the worker's transcripts under the start folder's name.
- fold keeps its own lines in `.fold/exclude`: the comment `# fold writes this file. To keep a path, add a ! line to .foldignore.` at the top, and after the user's lines `/.claude/skills/fold/`, `/.claude/skills/fold-area-lead/`, `/.claude/skills/fold-review-lead/`, `/.claude/skills/fold-task-worker/`, `/.claude/skills/fold-reviewer/`, `/.claude/skills/fold-main/` and `/.claude/settings.local.json`. fold writes its skills into the project folder and writes them again after each update, and every session reads them there or, for a worker other than the main agent, from the copy in its start folder, so they are never part of main; `.claude/settings.local.json` holds one person's Claude Code settings. The rest of `.claude`, such as `settings.json` and the project's own skills, agents and commands, is tracked as usual, also a skill of the project whose name starts with `fold-`. Each start of the daemon adds back a line of fold's that the file does not hold, so removing a line does not keep a path: a `!` line of `.foldignore` for its folder or file, such as `!/.claude/skills/fold/` or `!/.claude/settings.local.json`, keeps it tracked. When main still tracks files below fold's skill folders that the rules leave out, the daemon's next start of the project makes one revision of `fold` titled "Stop tracking fold's skill files" that removes them from main and leaves them on disk. The revision waits for a later start of the daemon while the project folder is not ready: main holds paths the user changed, the folder has not followed main, `HEAD` or the Git branch shows a change fold did not make (`head_moved`), commits of the user wait on the branch, a stash conflict or an unstash that stopped part-way waits, a change of the user waits for the main agent, or main or the folder's record changes the skill files while fold makes the revision. Meanwhile `fld status` names the skill folders main still tracks and the `fld untrack` command that stops tracking them at once. While Git sync is on, the revision is one commit on the `[git]` branch that removes the files from the branch and the index and leaves them in the work tree; a teammate's pull of that commit removes them from the teammate's folder until fold writes them there again. A tracked `.claude/settings.local.json` stays tracked until the user runs `fld untrack .claude/settings.local.json`.
- `.git` and `.fold` are never part of the tree. With Git sync on, `.gitignore` holds a `.fold/` line.
- A check's output, build folders and dependency folders belong in `.gitignore`, or the run fails with `files_changed`.
- A check command, and every worker but the main agent, runs with `GIT_CEILING_DIRECTORIES` set to a folder inside `.fold` and without `GIT_DIR` and `GIT_WORK_TREE`, so `git` there fails with "not a git repository" and never reaches the project's repository. A check that needs the tracked files lists the folder itself; an agent reads its changes with `get_workspace_changes` and history with `compare_revisions`.

## Commands

The user runs these in a terminal; agents never do. Commands that act on a project take the project from the current folder, or from `--project DIR` where it is offered, and most take `--socket` for a daemon on another socket. `fld <command> --help` shows every flag.

Start and set up:

- `fld` with no command: print fold's own state (not the project folder, which `fld status` shows): the fld version, whether the daemon runs, its web address and socket, whether a service runs it, and the project of the current folder. It never starts the daemon, and it names `fld restart` when the daemon runs another version.
- `fld init [DIR] [--name NAME] [--with-git] [--git-name NAME --git-email EMAIL]`: make the folder a fold project and register it. Without `DIR` the current folder; a new `DIR` is created. `--with-git` turns Git sync on: in a Git repository its `HEAD` commit becomes the genesis and fold's section in the instructions file becomes `r1`, a commit on the branch (an instructions file that Git does not track stays a change to record with `fld record`), else fold creates `.git`, and every revision becomes a commit on the `[git]` branch. The commit of an integrated proposal has the proposal title as its subject and the intent of the integrated version as its body: the summary and one `<name>: <what it does>` line per part; each member of a review batch is its own commit with its own intent. `fld init --refresh [DIR]` rewrites fold's Claude Code files (`AGENTS.md` or `CLAUDE.md` section, the skill and this file) in an existing project. fold never writes its skills into Claude Code's personal skill folder `~/.claude/skills`, where a skill of the same name hides the project's skill from every session: `fld init`, `fld init --refresh` and the skill writes of `fld claude` and the daemon refuse a project whose `.claude/skills` is that folder after symbolic links, such as a project in the home folder, with `invalid_request`, `details.reason` `personal_skill_folder` and a hint that names the project folder; `fld init` then creates nothing.
- `fld setup [--no-start] [--claude] [--remove]`: install the service that starts the daemon at login (a systemd user unit on Linux, a launchd agent on macOS) and start it, then offer to add fold to the user's Claude Code config. `--claude` only adds fold to Claude Code; `--remove` takes fold's entries out of it. The systemd unit has `OOMPolicy=continue`, `MemoryHigh=65%` and `MemoryMax=80%` in `[Service]`: when the kernel's OOM killer ends one process of the unit, such as one check, systemd keeps the daemon and its workers running (the default `OOMPolicy=stop` would stop the whole unit), and the unit's memory is slowed at 65% and capped at 80% of the host's memory. `fld setup` writes an older fold unit again with these lines; the launchd agent has no such lines.
- `fld claude [--name NAME] [--keep-others] [-- ARGS]`: start the daemon when needed and continue the main agent's last session, or start one. `fld new` (also `fld new claude`) starts a new main session and takes `--keep-others` too. The new session takes over the main agent's live sessions: `fld claude` names them first, fold sends each a last notice and closes its connection, and a reconnect of a taken-over session is refused with `main_session_taken_over`. With `--keep-others` the older sessions stay connected beside the new one. A reconnect of `fld mcp` after a daemon restart never takes over a session. A project with `supervised = true` under `[main]` refuses it with `main_supervised`.
- `fld serve [--listen ADDR] [--socket PATH] [--web-dir DIR]`: run the daemon in the foreground; the service runs it the same way.
- `fld mcp`: the stdio connection of a Claude Code session to the daemon, which Claude Code starts itself. When the daemon stops, such as for `fld restart` or an upgrade, it keeps the session open and connects again, with waits that grow from 0.1 s to 5 s, as the same agent; it never starts a daemon for that. A tool call while no daemon answers, and a call that ran when the daemon stopped, gets `daemon_restarting`. After 5 minutes without a daemon it ends with "the daemon closed the session; start a new session to reconnect". A main session that a newer `fld claude` took over does not connect again: the daemon refuses it with `main_session_taken_over`.
- `fld restart`: restart the daemon, so a newly installed fld takes over; supervised workers stop and continue in their sessions. After a start, the daemon runs the workers again in groups of 4 across all projects with a pause of 10 s between two groups, the workers with owed work and the leads first. A session keeps the skill it loaded, so the next turn of a worker whose session loaded another fld's skill text starts with a note to load its role skill again; a new fld with the same skill text sends no note.
- `fld doctor [--project DIR]`: check the host, the daemon and each project, and name the fix for each problem. It warns, never fails, when the installed systemd unit lacks `OOMPolicy=continue`, `MemoryHigh=` or `MemoryMax=` in `[Service]`, and names `fld setup` as the fix; it reads the unit file alone, not its drop-in files. The host check `personal skills` fails for each personal skill named `fold`, `fold-main`, `fold-area-lead`, `fold-review-lead`, `fold-task-worker` or `fold-reviewer` below `~/.claude/skills`, and its fix names the folders to remove; fold never deletes them. `fld claude` and `fld serve` print the same warning once at start.

Work in the project folder:

- `fld record`: record the user's changes in the project folder on main as one change of the user's. A conflict with the agents' work waits for the main agent in Needs you. It asks first, and names the files, when the change empties a tracked file, adds 10 or more empty files, or holds files that changed during a tool call of a supervised worker, which fold does not offer as the user's change until the user keeps, puts aside or ignores them; `fld record --yes` records without asking, and without a terminal and `--yes` it stops with the reason `needs_confirmation`, as `fld reset`, `fld restore` and `fld stash drop` do; over HTTP the daemon answers `record_needs_confirmation` with the `tree` to confirm. To put a worker's files aside instead, `fld restore <path>...` with those paths stashes them as `stash@{0}`, which `fld unstash` brings back, and brings main's version back. fold places a change in a tool call by the file's time (for a deleted file, its folder's): a change the user makes in the folder while a worker's tool call runs counts as the worker's too. Without a supervised worker's tool call, such as in a session opened by hand, fold sees no worker change. A restarted daemon knows only the tool calls since its start.
- `fld share <path>...`, `fld unshare <path>...`, `fld share --list`, `fld share --dismiss`: share ignored files or folders with every workspace through read-only links, stop sharing them, list the shared paths with the ignored paths workers cannot see, or end the Needs you items of shared files that changed while a worker worked (see `.fold/shared` above).
- `fld untrack <path>...`: stop tracking files of the project folder, like `git rm --cached` with its commit: one revision of the user removes every tracked path at or below each named path from main and leaves the files on disk. Other unrecorded changes stay unrecorded. Older revisions keep the files, so a leaked secret still needs to be changed. A file that no ignore rule matches is recorded again by the next `fld record`. A path main does not track is refused with `path_not_tracked`.
- `fld stash`: put the user's unrecorded changes aside, so the folder follows main again. `fld stash list` shows the entries, newest first.
- `fld stash drop [stash@{n}]` and `fld stash clear`: drop one entry, the newest by default, or every entry, for good; no file of the folder changes, and `fld gc` deletes their objects later. Only the user runs them: fld shows the entries and asks first, and `--yes` skips the question. A drop names the entry the user saw, so a stash that changed meanwhile is refused with `stash_changed` and nothing is dropped. An entry whose unstash conflict waits in the folder is refused until `fld record` finds the markers fixed or `fld reset` drops it. No agent drops the user's stash; when the user asks, tell them the command.
- `fld unstash`: merge the newest stash entry back into the folder; a conflict writes conflict markers and keeps the entry until `fld record`. fold notes the planned writes before the first one, so an unstash that stopped part-way is finished by the next `fld stash`, `fld unstash` or `fld record`, which names it in its answer; a path the user changed after the stop stays as it is.
- `fld reset` and `fld restore <path>...`: put the whole project folder, or only the named files and folders, back to the files fold last wrote there, so the folder follows main again. fold first stashes what they discard as `stash@{0}`, which `fld unstash` brings back, and a reset also drops the user's conflicted change that waits for the main agent and abandons the main workspace that holds its merge; a restore only withdraws it, and only when the named paths held all of the user's unrecorded changes, and leaves the main workspace open, so your notice asks you to abandon it. Only the user runs them: fld shows what it discards and asks first, and `--yes` skips the question. A reset never moves Git: a branch or HEAD that fold did not move, and Git commits that wait for the main agent, are refused as `fld stash` refuses them. No agent resets the folder; when the user asks, tell them the command, and when fold abandoned your main workspace, tell the user.
- `fld status [--json]`: show the project folder against main and change nothing: main's head and the revision the folder holds, each file `fld record` would record now (added, modified, deleted or a type change between a file and a symlink) with those main changed too, what keeps the folder from following main (a Git branch fold did not move, Git commits fold has not recorded, an unstash that stopped part-way, an unstash conflict, a conflicting change that waits for the main agent, files held by main) with the next step for each, the files a supervised worker changed with its agents and the steps that settle them, the shared paths and the ignored paths no worker sees, the number of tracked files that an ignore rule matches, listed only when one of them has a change (`--json` always lists them), and the stash with the entry `fld unstash` takes next. `--json` prints the daemon's answer.
- `fld pause` and `fld resume`: stop every worker of the project, keeping its session and claims, and run them again.
- `fld checks cancel RUN`, `fld checks cancel --task T-N` and `fld checks cancel --all`: cancel one running check run, every running run of the task, or every running run of the project. The running command stops, no later command starts, and each run fails with reason `cancelled`; the command prints each cancelled run id. Integration runs are not cancelled.
- `fld worker restart NAME [--instructions TEXT]`: start the worker `NAME` of any role again in a new Claude Code session, for example when its session is broken; it keeps its name, claims and workers, and its old session id stays in its previous sessions.
- `fld log [-n N] [--oneline]`: list main's revisions, newest first, as the web app's repository screen shows them: a line with the revision id and its title, then lines that start with `↳`: main's head marked, the proposal with its task and author or what the revision is (a pull, a direct change, a record, a change of main made by fold or the genesis), and the time in the user's local time zone with the Git commit; a blank line separates revisions. `-n` sets how many (20 by default, at most 1000); `--oneline` prints only the id and the title.
- `fld cost [--since WHEN] [--by SPLIT] [--task T-N] [--json]`: print what the project's supervised workers cost, from the values Claude Code reported: the total of all time, today and the last 7 days (local days, from midnight in the terminal's time zone), the tokens (cache read, cache write, output and input), then by role, by area and the top tasks with their build and review cost and their tokens. `--since` takes today, 12h, 7d, a date (from its local midnight) or an RFC 3339 time; `--by` prints one split in full (role, area, model, worker or task); `--task` prints one task's cost per worker; `--json` prints the daemon's answer. The main agent's own session is not supervised, so its cost is not counted.
- `fld transcript AGENT [--tail N]`: print the path of the agent's Claude Code transcript, the file of its current session: the main agent's recorded session, or the session fold runs for a worker. `--tail N` prints the file's last N lines instead; fld reads them itself, and the daemon never opens a transcript.

Maintenance and access:

- `fld gc [--dry-run]`: delete unreferenced objects, prune automatic checkpoints beyond `auto_checkpoints_kept`, remove the closed workspace directories that are due, remove the folders of finished workers, and prune the checkpoints of workspaces closed longer than `closed_workspace_days`. fold removes a workspace's directory as soon as the workspace closes and its owning agent has no running worker process and no open session, or once it closed longer than `closed_workspace_days` ago, so a lead whose process never ends does not keep its old review checkouts; an open session that works inside the directory keeps it in both cases. A final checkpoint of the tracked files fold had not recorded comes first (a review checkout takes none). That checkpoint is a record, not a restore point: a closed workspace is never restored. A directory that is at the path of a removed workspace again, such as one an agent wrote into by its full path after the removal, is removed again the same way, with a final checkpoint of what it holds; so is a directory found again after a removal that stopped before it was recorded, when it holds files fold has in no tree. fold never deletes across a mount: a directory on another file system than `.fold/ws` stays, with the reason `other_filesystem`. `fld gc` retries a removal that failed. fold also removes the folder `.fold/workers/<name>` of a task worker or reviewer that stopped or failed longer than `closed_workspace_days` ago and holds no claim, has no open session, is not parked, has no turn that waits and is owed no resume and no message; leads and the main agent keep theirs. Every file there is one fold writes again at the worker's next start, so a message that starts it later still works. The daemon removes those folders when it opens a project and in its daily collection. `--dry-run` changes nothing; both forms print the counts, then one line for each closed workspace not recorded as removed and each such worker folder, with what the run does with it and why, such as `workspace ws-2 .fold/ws/review-p-1: would remove, it closed more than closed_workspace_days ago` or `worker folder web-worker-3, 4120 bytes: kept, it holds a claim`.
- `fld web`: print a one-time link that signs the user in to the web app in a browser on this machine. The link works once, for a few minutes; fld prints when it expires and starts the daemon when needed.
- `fld token create USERNAME [--label TEXT]`: create a sign-in token for the web app for the person with the username `USERNAME`, for a browser that cannot open a link from `fld web`, such as one on another machine, and print it once. The daemon makes the token and starts when needed. `fld token list` shows the tokens without their secrets, and `fld token revoke ID` (such as `wt-3`) ends every session made from one.
- `fld web` and `fld token create` refuse a process that a fold worker or a fold check started, as fold refuses such a process that names a human. A `fld claude` session, such as the main agent in the user's own terminal, is the user's trusted terminal: it and the commands it runs can sign in as the user, while the workers that fold starts cannot. A process that left a worker's process tree, and any process of the user, can still read and write the user's files, fold's own files too, because agents run as the user's OS user. A browser sends the sign-in cookie to every port of the same host, so a local development server opened in the same browser, such as one that an agent started, can receive it. For full isolation, run the agents as a separate OS user or in a sandbox.
- `fld subscribe [EMAIL]`: subscribe an address to fold release news.

Notices (webhooks, Slack and Discord):

- `fld notify` (or `fld notify list`): list the notice targets that get the project's notices: its own and the host's while `fld notify host-targets` is on (the default), each with its id (such as `nt-3`), name, kind, URL without its path, events, card-move columns, window and health, then the host switch and the web address of links.
- `fld notify add webhook|slack|discord NAME [URL] [--host] [--events EVENTS] [--moves-to COLUMNS] [--window SECONDS]`: add a target. Without `URL`, fld reads it from the first line of standard input, so a Slack or Discord URL, which is the channel's secret, stays out of the shell history. A generic `webhook` gets a signed JSON body (Standard Webhooks: `webhook-id`, `webhook-timestamp`, `webhook-signature`); fld prints its `whsec_` signing secret once. `slack` and `discord` get one message with a line per notice. `--events` is `recommended` (the default), `all`, `needs-you-only` or event names separated by commas; `--moves-to` names the columns whose card moves the target gets (`review,done` by default); `--window` is the seconds after the first notice whose notices go in one send (15 by default, 0 sends each alone, at most 3600). `--host` adds a target of the host, which every project that uses the host targets sends to. A URL is `https`, or `http` only to localhost or a loopback address (`plaintext_notify_target`); fold never follows a redirect.
- `fld notify edit TARGET [--name NAME] [--url-stdin] [--events EVENTS] [--moves-to COLUMNS] [--window SECONDS] [--switch on|off]`, `fld notify remove TARGET`, `fld notify test TARGET` and `fld notify rotate TARGET`: change, remove, test or give a new signing secret to a target named by its id or its name. A test waits for the receiver's answer and goes into the send log; one that gets through turns on a target that fold turned off. After a rotation the old secret signs too for a day.
- `fld notify log TARGET`: the target's newest sends (fold keeps 50): the notices each carried, the status or error of its newest try, the try count and its `webhook-id`, which every try of a send keeps.
- `fld notify web-url [URL | --clear]`: show or set the address people open fold at; links in notices start with it, and without it notices carry no links. `fld notify host-targets [on|off]`: show or set whether the host's targets get the project's notices too.
- The events are `needs_you.opened`, `needs_you.closed`, `task.created`, `task.moved`, `task.blocked`, `task.sent_back`, `proposal.opened`, `review.approved`, `review.changes_requested`, `proposal.integrated`, `proposal.closed`, `integration.failed`, `checks.failed`, `worker.failed`, `git.failed`, `message.to_human`, `request.approved` and `project.paused`; a test sends `webhook.test`. A notice holds ids, titles, columns, names and links, never a message body, review text, diff or file content. A failed send tries again after 10 s, 1 min, 5 min, 30 min, 2 h and 6 h with the same `webhook-id`, honouring `Retry-After`. fold turns the target off when a send fails its last try (about 8.6 hours after its first), after 20 failed tries in a row, or at once on a 410 answer, and puts it into Needs you with the reason; a test send is one try. The Settings tab's Send again resends a finished send only while its target gets the project's notices (`notify_target_inactive` otherwise). The event `notify.target_changed` (`target`, `name`, `host`, `state`: `on`, `off`, `gone`, `failing` or `removed`) records each change of a target by a person and each time fold turns one off or on again. Only a person changes targets, never an agent; the daemon keeps them and their secrets in its own data folder, readable only by the user, and deletes a project's targets when the project leaves fold.

Claude accounts (the user's own subscriptions):

- `default` is Claude Code's own login, as `claude login` stores it on the host: it is first in every list and among the accounts to choose only while that login is there (on macOS in the keychain), and it holds no token of fold's. A project on it gives its workers no token, and a project shows it as its account also when the login is gone; its workers' turns then wait for a working login, and a new `claude login` on the host runs them again in their sessions. `.fold/config.toml` without the key `account` means it, and so do `account = "default"` and `account = "system-default"`. It cannot be added, updated or removed (`account_reserved`).
- `fld account add NAME`: keep a Claude subscription under the new name `NAME` (such as `work-a`) with the token that `claude setup-token` printed, read from standard input, never from an argument: `fld account add work-a < token.txt`, or paste it at the prompt, which hides it. The token stays in a file of mode 0600 in fold's data folder, never in a project folder, a log, an event or an answer. A name the host has already is refused (`account_exists`). Before it stores the token, fold checks it with one very small `claude -p` turn (the smallest model, no tools, no MCP servers, no saved session, a temporary folder, at most 60 seconds), which gets the token only in `CLAUDE_CODE_OAUTH_TOKEN`. A token that the API refuses is refused (`account_token_rejected`) and nothing is stored. When the turn cannot reach the model, the account is at a usage limit, no `claude` is on the PATH, the turn runs past 60 seconds or Claude Code ends it with another error, fold stores the token and prints a warning that it could not check it now, with a hint; `fld account update NAME` with the same token checks it again.
- `fld account update NAME`: give the account a new token the same way, as for an expired or revoked one, or when doctor says that a token is old. fold checks the new token in the same way; a refused token is refused (`account_token_rejected`) and the account keeps its old one. Each running worker of a project that uses it restarts in its own session with the new token before its next turn, a working one when its current turn ends, and every worker that starts or resumes from then on starts with it.
- `fld account list`: `default` while Claude Code has its own login on the host, then the accounts, each with when its token was added and the projects that use it, never the token. `fld account remove NAME` removes an account and its token, and is refused (`account_in_use`) while a project uses it.
- `fld account use NAME`: make `NAME` the account of the project in the current folder; it writes `account = "NAME"` into `.fold/config.toml`, and `fld account use default` removes the key; while Claude Code has no login of its own on the host, `default` is refused (`account_not_found`). The project's Settings in the web app choose it too. fold starts every worker of the project, and `fld claude` and `fld new` start the main agent, with that account's token in `CLAUDE_CODE_OAUTH_TOKEN`. After a change each worker continues in its own session with the new account when its current turn ends, an idle one at once, and loses no context; a running `fld claude` session keeps its account until it starts again. fold never switches the account by itself; at a usage limit, Needs you offers each other account in one Switch account control next to Pause: choosing an account switches at once.
- A refused login is a wait, not a failure: when the API refuses the token of the project's account, or Claude Code's own login for `default` (such as `Invalid API key · Please run /login`, `OAuth token has expired`, `Failed to authenticate: OAuth token revoked` or `API Error: 401 …`), each worker's turn waits and every view shows "Waits for a working login"; the turn is no failed turn and no stall, and claims stay fresh. Needs you shows one item for the project that names the account of the newest refused turn, also after a pause or a switch, "The token of work-a was refused" (for `default`, "Claude Code's login was refused"), with Pause, Switch account (never to an account whose login a turn found refused, until it gets a token newer than its newest refusal; for `default`, until a turn on it is answered) and that account's fix, which names a switch only when the item offers one: `fld account update work-a` with a new token, or `claude login` for `default`. A new token, a switch of the account (with `fld account use`, Settings or Needs you), a new Claude Code login or a daemon start runs each waiting turn again at once in its own session, once per change and never beside the own turn of a resume, which ends the item once the login works. Otherwise fold runs one waiting turn again after 10 minutes, then after twice as long each time, up to an hour, in case the login works again by itself; once that turn is answered, the other waiting turns run again. An answer of another worker runs no waiting turn again, since it can run on another login. `fld doctor` names the workers that wait for a working login. `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY` and a cloud provider's `CLAUDE_CODE_USE_*` in the workers' environment take the place of any account, and `fld doctor` warns about them.

Git remotes (with Git sync on):

- `fld remote add NAME URL [BRANCH]`, `fld remote remove NAME` and `fld remote list` (also plain `fld remote`) manage `[remotes.<name>]`.
- `fld push [NAME]`: push main's history, one commit per revision, without force. The name can be left out when the project has one remote.
- `fld pull [NAME]`: bring the remote's commits into main; a conflict becomes a sync task.
- `fld git branch NAME`: rename the local Git branch that each integration commits fold main to, and `[git] branch` in `.fold/config.toml` with it; the commits, the remotes and their branches stay. Only a human renames it (`human_required` for an agent). It refuses with `invalid_request` and `details.reason` `branch_exists` when the branch exists, `head_moved` when `HEAD` is not on the configured branch, and `folder_held` while a Git operation is half done or `fld status` names a blocker. When the folder is on another branch, fold's hint names `git switch` to the configured branch only when that branch exists, else `fld git branch` with the checked-out branch.

Host config. `$XDG_CONFIG_HOME/fold/daemon.toml` (else `~/.config/fold/daemon.toml`) holds `listen` (the web address, `127.0.0.1:7420` by default), `socket`, `session_days` (how long a web sign-in lasts, 30 days by default), `check_runs` (the most check runs at once across all projects, half the processors by default) and `check_memory_gb` (the free memory in GiB a check run waits for before its commands start; the larger of 4 GiB and 10% of the total memory by default). Each of the three numbers is a positive whole number: a zero, a negative or a text value stops the start. The daemon reads it at its start, so an edit needs `fld restart`.

## Web app

The daemon serves the web app at `http://127.0.0.1:7420` by default. Every browser signs in, on loopback too, so a request that only names a person acts as nobody; this does not keep agents away from the user's files, as the access commands above state. A person opens the link that `fld web` prints, or enters a token from `fld token create` on the sign-in screen. Each project has these tabs, and every write a person makes there goes through the same commands as an agent's:

- Board: the five columns of the tasks, Backlog, To do, In progress, Review and Done, with search and the Attention, Labels, Owner and Blocked only filters, where Labels and Owner take several ticks (any ticked entry matches, and the filters together must all match) and Owner holds Human with the human tasks, Main agent with the other tasks of the area Main and the tasks in no area, and each area lead with all of its area's tasks, its human tasks too; a lead's row in the Agents panel or a mention of a lead or of the main agent opens the board with that owner ticked; a phone shows one column at a time with a column switcher. The board is read only; cards move when fold's state changes. Each card shows one line about its work and at most one chip, and its details on hover or focus. The details stay below the top bar and inside the window and scroll; a report or hold reason longer than four lines shows its first four lines and Open the task to read the full report. A card with a question for you has Mark answered in its details, for an answer you gave elsewhere. While a check run goes in the holder's workspace, the card's line says Running checks, or Running checks for v1 before a new proposal, or Running checks for v2 when the run makes the proposal's next version, and its chip says Running checks in the neutral tone: no person waits for the run, and the worker is not stalled. A worker that waits for a person's answer is not stalled either. fold reads the output of each worker it runs: while a tool call has been open for a minute or more the chip says what it does in the neutral tone, such as Running a command for 8 min. The chip says what fold saw when the worker stalls: No activity from @worker for 12 min (no open call and no output for `stall_minutes`), A command of @worker has run for 25 min (a command open for 20 minutes, twice Claude Code's 10-minute limit; a subagent or another tool after 20 minutes without output; a fold call never counts as long), or @worker failed (its process ended by a crash or a failure that nobody asked for, without a report). A worker that a person, an agent or fold stopped shows @worker stopped in the neutral tone and is not stalled. A worker that its lead parked with `stop_worker`'s `wait_for` shows Waits for @lead's go in the neutral tone, with what it waits for in the card's details, the task, Activity and the Agents table, until the lead's message resumes it in its session; its claims do not go stale while the lead runs. When fold saw nothing of the worker, the card's line names the file of the last edit and its time. fold tells the worker's lead first, or the main agent for a worker without a lead, with the tool that starts it again (event `worker.stalled`): `restart_worker`, which the main agent calls for a stalled worker and otherwise on the user's word, and the lead that started the worker calls for it. The chip turns gold and Needs you lists the stall only when it lasts one more `stall_minutes` after that, or at once when no agent can act. A stopped worker whose resume fold owes, such as for requested changes or a send-back, while the worker limits are full is not stalled: its chip says Waiting for a free slot in the neutral tone, fold tells nobody and Needs you lists nothing, and fold resumes it before any other start of its role once a slot frees; it counts as stalled only when a slot was free for one `stall_minutes` and it still did not start. A worker that waits for its group after a daemon start shows Waiting for a free slot in the same way and is not stalled. While the project is paused, no worker is stalled. The card's details, the task and Needs you then name whom fold told and offer Restart worker, which does what `fld worker restart <name>` does and stays pending until the daemon answers. fold keeps the times of the workers' output in memory, so after a daemon start it counts from that start. A question or a review for you, a hold or an unfinished prerequisite still shows over it. The worker's claims do not run out while its own run goes, and they get a full lease from the run's end, so a stale claim shows only after the run. A claim never runs out while its holder waits on others: its proposal waits for review or integration, its ask waits for you, its report waits for the lead, or, for a reviewer, its verdict is in, nor while its turn waits for the network, a usage limit or a working login, after which the lease counts again from the end of the wait. fold tells the holder's lead of a stale claim first, or the main agent (event `claim.stale`); the card shows it in gold with what you do, Stale claim · message worker or Stale claim · restart worker, and Needs you lists it only when no agent that can act runs or when it lasts one more `stall_minutes` (event `claim.needs_person`); an agent counts as told only while its process runs or it has an open session. A renewal that clears the mark, by any fold call of the holder, the end of its check run, a resume of the project or fold's renewal of a holder that waits, appends `claim.renewed` with the task and the holder (`{"task": "T-1", "agent": "web-worker"}`). Every gold mark of a stall or a stale claim names what you do. An open proposal says P-3 being reviewed while a reviewer holds its review claim, with the reviewer's name in the card's details, the task and the proposals list, and waits for review only while no reviewer holds it. The needs line of a card in Backlog and its Blocked badge name the first 3 prerequisites and +N more; the card's details and the task list them all. New task opens a form (title, description, area and labels, who does the work), which suggests a request first.

- Requests: create a request with attachments; on a request, approve a draft, request changes, edit the draft into a new version, close it and answer its clarification thread. ## Tools

Every fold tool by purpose; the skill holds their arguments and workflows. The heavy reads answer in a short form by default and name the full form in their descriptions: `get_proposal` with `detail` `full` adds the evidence text, the whole intent (the short form gives its summary and each part's name with its `file_count`), the task description and the whole earlier review bodies; `get_task` with `history` `all` gives every history entry the read holds instead of the newest 5; `get_task_graph` with `include_done` adds the Done tasks, which `done_count` counts, and with `detail` `full` the empty `labels`, `needs` and `holder` that it leaves out; `list_workers` with `include_stopped` lists the stopped workers, with `include_instructions` each area's instructions and with `include_handoffs` the text of each newest hand-off note; `get_check_run` with `detail` `full` lists every command of the run, not only the failed ones. `get_proposal_diff` and `compare_revisions` give each hunk as a unified `@@` header with the first line and the line count of each side, and one string per line: a mark (space, `-` or `+`), the line's number, a space and the text, such as `+14 let x = 1;`. A removed line has its old number and a context or added line its new number, so a comment uses the number on the line.
