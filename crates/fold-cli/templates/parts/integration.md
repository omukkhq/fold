## Integration

fold integrates a ready proposal by itself when the project integrates automatically, which is the default: a reviewer, the main agent or a human approved it, nothing asks for changes, a marked task has an approval by a human that the mark accepts, and every prerequisite task is Done. In a project that does not integrate automatically, call `integrate_proposal(id, expected_version?)` when the proposal is ready. Pass the version you reviewed as `expected_version`: if a newer version exists, the call fails with `stale_version`. fold checks the approvals, the human review mark and the prerequisite tasks before it moves main. The approved members of a submitted review batch integrate together: once every member has its final state for the batch (approved, or out because changes were requested, it was rejected, closed or removed, or it waits for a human or for a member that is out), fold merges the approved ones onto main in dependency order, runs the integration checks once on the whole merge, and publishes one revision per member in one step. A member that conflicts goes alone to the reviewer that approved it, as for a single proposal. When that one check run fails, fold integrates the members one at a time, each with its own run, and only a member whose own run fails goes back. A member that is out, such as one released `reviewed_alone`, integrates later on its own rules. An hour after the batch review, a member that still has no final state is out too. In a project that does not integrate automatically, call `integrate_review_batch(id)` for a ready batch; it refuses a batch with members that have no final state with `invalid_request` and the reason `batch_waiting`. `integrate_proposal` still integrates one member alone.

When the integration of an approved version conflicts with main, the author gets no notice: fold gives the conflict to the reviewer that approved the version and still holds its review claim, in its next turn or by a resume, with `integration.conflicted` naming it in `data.fixer`. That reviewer's `create_review_checkout` holds the version merged onto the current main with conflict markers and `.fold-main` sides, and `submit_review_fix` refuses a leftover one with `unresolved_conflicts`. Without such a reviewer, or when the resume cannot run, the review lead gets a notice to start one, or the main agent for a task of `main`. The task stays in Review meanwhile. Failed integration checks go back to the author, except as the serial lanes below say.

The `[[serial]]` lanes of main's `fold-checks.toml` integrate one at a time. An open proposal whose current version changes a path of a lane is a member; the members go in the order of their first approval on any version, then by number, and members without an approval wait behind them. Only the front member integrates: `integrate_proposal` refuses another with `invalid_request`, the reason `lane_held`, and its `lane` and `position`, and the automatic and batch integrations wait the same way. `get_proposal`, `list_proposals` and `list_workers` show the lane and the position. When a member conflicts or fails its integration checks and main changed a lane path since the version's base, the failure goes to the reviewer that approved it, with a note that the lane moved. fold runs the integration queue and the lanes itself: no agent orders, holds or retries them by hand.
