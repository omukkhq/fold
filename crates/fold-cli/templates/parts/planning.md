## Orchestrator

An orchestrator keeps the task graph correct and the workers busy.

1. Read the graph with `get_task_graph` and one task with `get_task(id)`. Read what each worker does with `get_activity(agent?)`: claims, workspaces with changed files, latest checkpoints and open proposals.
2. Publish an approved set with `create_task_plan(tasks[])`. Give each task a unique `key` of 1 to 32 ASCII letters, digits, `-` or `_`, distinct from a public task id; `title`, `description`, `labels`, optional `kind` (`proposal`, `no_proposal` or `human`), `needs`, `parent`, `human_review`, `blocker` and `checklist` complete it. Put a task's plain steps in `checklist` as `[{text, checklist?}]` (without `checklist` a step goes to Subtasks, or to the only checklist the task has; with two or more checklists name one, or the plan is refused with `checklist_ambiguous` and nothing is created): the steps then exist before any worker sees the task, so do not add them with `add_checklist_item` after the plan. Each reference in `needs` or `parent` names an existing task id or a key in this plan. A review mark has `reason` and optional `reviewer`; a blocker has `reason`. `main_approves: true` on a task of `main` without `human_review` records that the user lets the main agent approve its proposal, so fold leaves its mark off; another task with it is refused with `invalid_request` and reason `main_approves`. The command creates 1 to 100 tasks, their edges, parent links, marks, blockers and checklist items in one transaction, calculates all statuses, then sends notices. A refusal creates nothing. For larger work, publish complete dependency groups in prerequisite order, with all children of a new parent together. The main agent or a human publishes any area; an area lead publishes only its own. Keep a split within the approved scope and copy the parent's human review requirement to its children.
3. For a single task without a human review requirement or other unpublished tasks, use `create_task(title, description?, labels?, needs?, parent?, kind?)`. Include prerequisites and parent during creation. Use the task template below, kind `no_proposal` for work that changes no project file, such as screens drawn through an MCP server (see Task kinds), and kind `human` for work that only a person can do outside every agent, such as "Verify the app on Meta". Make the tasks that wait for that work need the human task. Change title, description or labels with `update_task`, and remove work with `delete_task` or `archive_task`. Removal of held work is restricted to its agent, its lead or a human.
4. Add a dependency to existing work with `add_dependency(task, needs)` and remove one with `remove_dependency`. A cycle fails with `dependency_cycle`.
5. Link existing children with `add_checklist_item(task, text? / linked_task?, checklist?)`. With `linked_task` the item follows the child task, and fold ticks it when the child is Done. Change a plain item with `update_checklist_item(id, text?, done?)`. Move an item with `move_checklist_item(id, position, checklist?)`: position counts from 0, and `checklist` moves it within the same task. Remove an item with `remove_checklist_item`. Done checklists are locked; create new work for additions. The rights of archive and delete apply: on a task that a worker holds, only that worker's agent, its lead, the main agent or a human changes the checklist; on a task nobody holds, only the lead of the task's area, the main agent or a human. Anyone else gets `checklist_denied`, also from `create_task` with a `parent`. A plain item without `checklist` goes to the only checklist of the task, or to Subtasks when it has none; with two or more checklists it is refused with `checklist_ambiguous`.
6. Sort tasks with labels. Make one with `create_label(name, color)`. A task carries any number of labels that belong to no area, but at most one area label: fold refuses a second one on every create and update with `invalid_request` and reason `two_areas`. `get_task` marks a task that carries two area labels with `areas_conflict`; its title and description change freely, but each change of its labels must leave one area label. Human review marks remain until a human clears them.
7. When agent work must wait until a person says it can start, give a new task its `blocker` in `create_task_plan`, or call `set_blocker(id, reason)` on an existing task while it waits in Backlog or Todo, before an agent starts it. A task with a claim, a workspace or an open proposal is refused with `task_hold_denied`. While the blocker is set, no agent claims the task, no lead starts a task worker for it and `get_ready_tasks` leaves it out; its status does not change. Use a human task when a person has work to do, and a blocker when agent work only waits for a person's word. Only a human, the main agent or the lead of the task's area sets a blocker, and only a human or the main agent clears it with `clear_blocker(id)`.
8. A Claude Code subagent that you spawn works for you; fold does not know it (see Subagents). It cannot expand your role or assignment.

A task is ready when its dependencies are Done and nobody holds it. Stalled and stale are two different states. A claim is stalled when its workspace had no file change for 5 minutes (`stall_minutes`) and runs no checks. After a check run in the workspace, the 5 minutes count from the end of the run. This only shows on the board. A claim is stale when its 30-minute lease (`lease_minutes`) ran out. A stale claim allows `takeover_claim`.

## Task template

Write the description of every task in this form:

- A summary paragraph that says what the task delivers.
- **Refs**: the documents, tasks and code the worker must read.
- **Scope**: what to build, with the files or modules.
- **Out of scope**: what belongs to other tasks.
- **Acceptance**: the checks that show the task is done, each one testable.

Write dependencies as edges with `add_dependency`, never as text in the description.

## Drafting requests

The main agent turns a request into cards. The main agent is the agent with the `main` tag: `fld claude` gives it to the user's own interactive session in the handshake of its adapter. `register_agent` never gives the tag: a session opened by hand that asks for it gets `main_tag_denied`. One agent at most has the tag, and a worker that fold started never has it. An area lead may also claim a request that it finds relevant to its area; fold does not check the request against the area.

1. When a request is created, the main agent and every area lead get a push, except the requester's own agent. Call `list_requests(state?, kind?, mine?)` to see the requests, and `get_request(id, version?)` to read one: the message, the attachments, `code` for a request a human made on selected lines (the path, the lines, an excerpt and the revision, or the proposal, version and side they were read from), the latest draft (or the draft `version`), the comments of the requester, the id of the clarification thread and the tasks of an approval.
2. Call `claim_request(id, kind, title)`. Only the main agent or an area lead claims; another agent gets `orchestrator_required`. The kind is `bug`, `feature` or `question`, as you read the message. Write the title from the message: one line, at most 200 characters.
3. When the message is not clear, ask with `send_message(to[], body, request)`. The message goes into the clarification thread of the request, and `get_thread(request)` reads that thread. Anyone can write there. A message does not change the request.
4. Write the draft with `submit_request_draft(id, cards[], edges[]?, note?, kind?, title?)`. A draft has 1 to 20 cards. Each card has a `key`, a `title` and a `description` in the task template below. Each edge names the `prerequisite` card and the `dependent` card. Write dependencies as edges, never as text in a description. Give a card the `label` of the area that must build it, or `main` for work only the main agent can do. Approval gives the task this label. The label must exist, so call `create_label` first; an unknown label fails with `label_not_found`. The label `main` always exists.
5. When the requester asks for changes, you get a push. Read the comment with `get_request`, then submit the next version.
6. Call `release_request(id)` when you cannot finish the draft. Another orchestrator can then claim the request.

When a task becomes ready and nobody holds its claim, fold sends a push to the lead of its area, the area whose label the task carries, with `start_worker` as the next tool. The cards of an approved request become ready this way, and so do the dependents of an integrated task. When the area has no lead, the main agent gets the push and starts the lead. When the task has no area, the main agent gets the push and gives the task a label with `update_task`. A task of `main` goes to the main agent with `claim_task` as the next tool.

The approval creates one task for each card and one dependency for each edge, in one step. fold calculates the column of each new task: a task whose prerequisites are not Done is in Backlog, and the other tasks are in Todo. The drafter gets a push with the new task ids.
