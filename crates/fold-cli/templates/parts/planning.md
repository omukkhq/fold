## Orchestrator

An orchestrator keeps the task graph correct and the workers busy.

1. Read the graph with `get_task_graph(area?)` and one task with `get_task(id)`. `get_task_graph`, `get_ready_tasks`, `list_workers` and `wait_for_events` take an `area`, such as `web`, and keep only that area's tasks and workers; a lead passes its own area, and an unknown one fails with `area_not_found`. Read what each worker does with `get_activity(agent?)`: claims, workspaces with changed files, latest checkpoints and open proposals.
2. Publish an approved set with `create_task_plan(tasks[])`. Give each task a unique `key` of 1 to 32 ASCII letters, digits, `-` or `_`, distinct from a public task id; `title`, `description`, `labels`, optional `kind` (`proposal`, `no_proposal` or `human`), `needs`, `parent`, `human_review`, `hold` and `checklist` complete it. Put a task's plain steps in `checklist` as `[{text, checklist?}]` (without `checklist` a step goes to Subtasks, or to the only checklist the task has; with two or more checklists name one, or the plan is refused with `checklist_ambiguous` and nothing is created): the steps then exist before any worker sees the task, so do not add them with `add_checklist_item` after the plan. Each reference in `needs` or `parent` names an existing task id or a key in this plan. A review mark has `reason` and optional `reviewer`; a hold has `reason`. `main_approves: true` on a task of `main` without `human_review` records that the user lets the main agent approve its proposal, so fold leaves its mark off; another task with it is refused with `invalid_request` and reason `main_approves`. The command creates 1 to 100 tasks, their edges, parent links, marks, holds and checklist items in one transaction, calculates all statuses, then sends notices. A refusal creates nothing. For larger work, publish complete dependency groups in prerequisite order, with all children of a new parent together. The main agent or a human publishes any area; an area lead publishes only its own. Keep a split within the approved scope and copy the parent's human review requirement to its children.
3. For a single task without a human review requirement or other unpublished tasks, use `create_task(title, description?, labels?, needs?, parent?, kind?)`. Include prerequisites and parent during creation. Use the task template below, kind `no_proposal` for work that changes no project file, such as screens drawn through an MCP server (see Task kinds), and kind `human` for work that only a person can do outside every agent, such as "Verify the app on Meta". Give a human task the "How to do it" section of the task template. Make a human task only for work that no agent and no check can do: when an agent or a check can do the work, make an agent task. Make the tasks that wait for that work need the human task. Change title, description or labels with `update_task`, and remove work with `delete_task` or `archive_task`. Removal of held work is restricted to its agent, its lead or a human.
4. Add a dependency to existing work with `add_dependency(task, needs)` and remove one with `remove_dependency`. A cycle fails with `dependency_cycle`.
5. Link existing children with `add_checklist_item(task, text? / linked_task?, checklist?)`. With `linked_task` the item follows the child task, and fold ticks it when the child is Done. Change a plain item with `update_checklist_item(id, text?, done?)`. Move an item with `move_checklist_item(id, position, checklist?)`: position counts from 0, and `checklist` moves it within the same task. Remove an item with `remove_checklist_item`. Done checklists are locked; create new work for additions. The rights of archive and delete apply: on a task that a worker holds, only that worker's agent, its lead, the main agent or a human changes the checklist; on a task nobody holds, only the lead of the task's area, the main agent or a human. Anyone else gets `checklist_denied`, also from `create_task` with a `parent`. A plain item without `checklist` goes to the only checklist of the task, or to Subtasks when it has none; with two or more checklists it is refused with `checklist_ambiguous`.
6. Sort tasks with labels. Make one with `create_label(name, color)`. A task carries any number of labels that belong to no area, but at most one area label: fold refuses a second one on every create and update with `invalid_request` and reason `two_areas`. `get_task` marks a task that carries two area labels with `areas_conflict`; its title and description change freely, but each change of its labels must leave one area label. Human review marks remain until a human clears them.
7. When agent work must wait until a person says it can start, give a new task its `hold` in `create_task_plan`, or call `set_hold(id, reason)` on an existing task while it waits in Backlog or Todo, before an agent starts it. A task with a claim, a workspace or an open proposal is refused with `task_hold_denied`. While the hold is on, no agent claims the task, no lead starts a task worker for it and `get_ready_tasks` leaves it out; its status does not change. Use a human task when a person has work to do, and a hold when agent work only waits for a person's word. A hold never waits for a task: when a task must wait for another task, call `add_dependency`. When agent work waits for a person's word, put the hold on the earliest task of that work, not on its dependents: the dependents stay in Backlog until that task is Done, and a task on hold never becomes Done. Put holds on several tasks only when they do not depend on each other. Only a human, the main agent or the lead of the task's area puts a task on hold, and only a human or the main agent takes the hold off with `clear_hold(id)`.
8. A Claude Code subagent that you spawn works for you; fold does not know it (see Subagents). It cannot expand your role or assignment.

A task is ready when its dependencies are Done and nobody holds it. Stalled and stale are two different states. fold reads the output of each worker it runs. A worker with an open tool call works. It is stalled when no call is open and it wrote nothing for 5 minutes (`stall_minutes`), when a command is open for 20 minutes, twice Claude Code's 10-minute limit, or when its process failed, ended by a crash or a failure that nobody asked for, without a report. A worker that a person, an agent or fold stopped is not stalled. A worker that waits for a person's answer or for its own checks is not stalled, nor is a stopped worker whose resume fold owes while the worker limits are full: it waits for a free slot, and fold resumes it first when one frees. It counts as stalled only when a slot was free for 5 minutes and it still did not start. While the project is paused, no worker is stalled. fold tells the worker's lead of a stall, or the main agent when the worker has no lead. The notice names the next tool: `restart_worker` starts the worker again in a new session, which the lead that started it and the main agent may call, and `send_message` wakes it in its own session. The notice also ends a `wait_for_events` of the agents it names, whatever `types` says. A person sees the stall only when it lasts 5 more minutes after the notice. A worker that a lead parked with `stop_worker(name, wait_for)` waits for that lead's go: it is not stalled, and every view shows "Waits for @lead's go" until the lead's message resumes it. A claim is stale when its 30-minute lease (`lease_minutes`) ran out. A claim does not run out while its holder's own check run goes, and the lease counts again from the end of the run. The claims of a parked worker do not run out while the agent that parked it runs, nor do the claims of a holder that waits on others: its proposal waits for review or integration, its ask waits for a person, its report waits for the lead, or, for a reviewer, its verdict is in, nor while its turn waits for the network, a usage limit or a working login; the lease counts again from the end of that wait. fold tells the holder's lead of a stale claim, or the main agent when the holder has no lead (event `claim.stale`), as it does for a stall; a person sees it only when no agent can act, or when it lasts 5 more minutes after the notice. A stale claim allows `takeover_claim`.

## Task template

Write the description of every task in this form:

- A summary paragraph that says what the task delivers.
- **Refs**: the documents, tasks and code the worker must read.
- **Scope**: what to build, with the files or modules.
- **Out of scope**: what belongs to other tasks.
- **Acceptance**: the checks that show the task is done, each one testable.
- **How to do it** (every task of kind `human`, and only those): numbered steps that a person can follow without reading the code. Each step names one action, where to do it and what the person sees when it works. When the steps need a script or a tool, an agent task builds it first, and the human task needs that task.
- **Decisions** (optional, always last): one entry for each decision a person gave after the task was written, in the form that the `fold` skill's `REFERENCE.md` gives. The Scope and Acceptance text already says the decided value.

Write dependencies as edges with `add_dependency`, never as text in the description.

## Drafting requests

The main agent or the lead of the request's area turns a request into cards. The main agent is the agent with the `main` tag: `fld claude` gives it to the user's own interactive session in the handshake of its adapter. `register_agent` never gives the tag: a session opened by hand that asks for it gets `main_tag_denied`. One agent at most has the tag, and a worker that fold started never has it. An area lead drafts the requests of its area and may also claim another request that it finds relevant to its area; fold does not check a claim against the area.

1. A request has an area: the one that `create_request(body, attachments?, ws?, area?)` names, else the area of the requester's worker, and none for a human, the main agent or a worker outside an area. When a request of an area with a lead is created, only that lead gets a push. A request without an area, or of an area without a lead, goes to the main agent and every area lead, except the requester's own agent. When nobody claims a request of an area within `request_escalate_minutes` of `.fold/config.toml` (10 by default, counted from the latest resume after a pause), fold escalates it once with `request.escalated`, which goes to the main agent and every area lead. The main agent drafts only a request with no area, one with work in several areas, or one that needs the user, and leaves the others to the lead of their area. A `wait_for_events` of theirs ends at once when a request is created or released and nobody drafts it, whatever `types` says, and names it in `requests`. At each start or resume of their session, fold's context names the requests that wait for a drafter under `Requests to claim`, so a request made while the session was not running still reaches them: read each one and claim the requests you will draft. Call `list_requests(state?, kind?, mine?)` to see the requests, and `get_request(id, version?)` to read one: the message, the attachments, `code` for a request a human made on selected lines (the path, the lines, an excerpt and the revision, or the proposal, version and side they were read from), the latest draft (or the draft `version`), the comments of the requester, the id of the clarification thread and the tasks of an approval. Read one attachment with `get_request_attachment(id, n, offset?)`, where `n` is the 1-based position that `get_request` lists. A text file comes in pages of at most 256 KiB: the result holds `text`, its `offset` and `next_offset`, and `next_offset` is null on the last page; give it as `offset` to read the next page. An image (png, jpeg, gif or webp) of at most 5 MiB comes as image content. Any other file, or an image over 5 MiB, gives only its name, size and media type, with `content` `none` and a reason.
2. Call `claim_request(id, kind, title)` before you research the request, so that nobody else drafts it. Only the main agent or an area lead claims; another agent gets `orchestrator_required`. On `already_claimed`, the hint names the drafter: send it what you know with `send_message` and the `request`. The kind is `bug`, `feature` or `question`, as you read the message. Write the title from the message: one line, at most 200 characters.
3. When the message is not clear, ask with `send_message(to[], body, request)`. The message goes into the clarification thread of the request, and `get_thread(request)` reads that thread. Anyone can write there. A message does not change the request.
4. Write the draft with `submit_request_draft(id, cards[], edges[]?, note?, kind?, title?)`. A draft has 1 to 20 cards. Never call `submit_request_draft` in the same batch of tool calls as `claim_request`: claim first, read the result, then draft. Each card has a `key`, a `title` and a `description` in the task template below, and optionally a `kind` (`proposal` by default, `no_proposal` or `human`) and `needs`, the ids of existing tasks that the card's task must wait for. An unknown task in `needs` fails with `task_not_found`, and a `no_proposal` or `human` card that your role may not choose for its area fails with `task_kind_denied`. Each edge names the `prerequisite` card and the `dependent` card. Write dependencies as edges, never as text in a description. Give a card the `label` of the area that must build it, or `main` for work only the main agent can do. Approval gives the task this label. The label must exist, so call `create_label` first; an unknown label fails with `label_not_found`. The label `main` always exists. Draft only the cards that the requester's message asks for. When a card carries a decision or a document from the user, or adds behaviour beyond the requester's message, the main agent shows the cards to the user as a plan summary first and submits the draft only after the user's OK.
5. When the requester asks for changes, you get a push. Read the comment with `get_request` (and an attachment with `get_request_attachment`), then submit the next version.
6. Call `release_request(id)` when you cannot finish the draft. Another orchestrator can then claim the request.

When a task becomes ready and nobody holds its claim, fold sends a push to the lead of its area, the area whose label the task carries, with `start_worker` as the next tool. The cards of an approved request become ready this way, and so do the dependents of an integrated task. When the area has no lead, the main agent gets the push and starts the lead. When the task has no area, the main agent gets the push and gives the task a label with `update_task`. A task of `main` goes to the main agent with `claim_task` as the next tool.

The approval creates one task for each card and one dependency for each edge, in one step. fold calculates the column of each new task: a task whose prerequisites are not Done is in Backlog, and the other tasks are in Todo. The drafter gets a push with the new task ids.
