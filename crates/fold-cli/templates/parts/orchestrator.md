## Orchestrator

An orchestrator keeps the task graph correct and the workers busy.

1. Read the graph with `get_task_graph(area?)` and one task with `get_task(id)`. `get_task_graph`, `get_ready_tasks`, `list_workers` and `wait_for_events` take an `area`, such as `web`, and keep only that area's tasks and workers; a lead passes its own area, and an unknown one fails with `area_not_found`. Read what each worker does with `get_activity(agent?)`: claims, workspaces with changed files, latest checkpoints and open proposals.
2. Publish an approved set with `create_task_plan(tasks[])`. Give each task a unique `key` of 1 to 32 ASCII letters, digits, `-` or `_`, distinct from a public task id; `title`, `description`, `labels`, optional `kind` (`proposal`, `no_proposal` or `human`), `needs`, `parent`, `human_review`, `hold` and `checklist` complete it. Put a task's plain steps in `checklist` as `[{text, checklist?}]` (without `checklist` a step goes to Subtasks, or to the only checklist the task has; with two or more checklists name one, or the plan is refused with `checklist_ambiguous` and nothing is created): the steps then exist before any worker sees the task, so do not add them with `add_checklist_item` after the plan. Each reference in `needs` or `parent` names an existing task id or a key in this plan. A review mark has `reason` and optional `reviewer`; a hold has `reason`. `main_approves: true` on a task of `main` without `human_review` records that the user lets the main agent approve its proposal, so fold leaves its mark off; another task with it is refused with `invalid_request` and reason `main_approves`. The command creates 1 to 100 tasks, their edges, parent links, marks, holds and checklist items in one transaction, calculates all statuses, then sends notices. A refusal creates nothing. For larger work, publish complete dependency groups in prerequisite order, with all children of a new parent together. The main agent or a human publishes any area; an area lead publishes only its own. Keep a split within the approved scope and copy the parent's human review requirement to its children.
3. For a single task without a human review requirement or other unpublished tasks, use `create_task(title, description?, labels?, needs?, parent?, kind?)`. Include prerequisites and parent during creation. Use the task template below, kind `no_proposal` for work that changes no project file, such as screens drawn through an MCP server (see `.claude/skills/fold/KINDS.md`), and kind `human` for work that only a person can do outside every agent, such as "Verify the app on Meta". Give a human task the "How to do it" section of the task template. Make a human task only for work that no agent and no check can do: when an agent or a check can do the work, make an agent task. Make the tasks that wait for that work need the human task. Change title, description or labels with `update_task`, and remove work with `delete_task` or `archive_task`. Removal of held work is restricted to its agent, its lead or a human.
4. Add a dependency to existing work with `add_dependency(task, needs)` and remove one with `remove_dependency`. A cycle fails with `dependency_cycle`.
5. Link existing children with `add_checklist_item(task, text? / linked_task?, checklist?)`. With `linked_task` the item follows the child task, and fold ticks it when the child is Done. Change a plain item with `update_checklist_item(id, text?, done?)`. Move an item with `move_checklist_item(id, position, checklist?)`: position counts from 0, and `checklist` moves it within the same task. Remove an item with `remove_checklist_item`. Done checklists are locked; create new work for additions. The rights of archive and delete apply: on a task that a worker holds, only that worker's agent, its lead, the main agent or a human changes the checklist; on a task nobody holds, only the lead of the task's area, the main agent or a human. Anyone else gets `checklist_denied`, also from `create_task` with a `parent`. A plain item without `checklist` goes to the only checklist of the task, or to Subtasks when it has none; with two or more checklists it is refused with `checklist_ambiguous`.
6. Sort tasks with labels. Make one with `create_label(name, color)`. A task carries any number of labels that belong to no area, but at most one area label: fold refuses a second one on every create and update with `invalid_request` and reason `two_areas`. `get_task` marks a task that carries two area labels with `areas_conflict`; its title and description change freely, but each change of its labels must leave one area label. Human review marks remain until a human clears them.
7. When agent work must wait until a person says it can start, give a new task its `hold` in `create_task_plan`, or call `set_hold(id, reason)` on an existing task while it waits in Backlog or Todo, before an agent starts it. A task with a claim, a workspace or an open proposal is refused with `task_hold_denied`. While the hold is on, no agent claims the task, no lead starts a task worker for it and `get_ready_tasks` leaves it out; its status does not change. Use a human task when a person has work to do, and a hold when agent work only waits for a person's word. A hold never waits for a task: when a task must wait for another task, call `add_dependency`. When agent work waits for a person's word, put the hold on the earliest task of that work, not on its dependents: the dependents stay in Backlog until that task is Done, and a task on hold never becomes Done. Put holds on several tasks only when they do not depend on each other. Only a human, the main agent or the lead of the task's area puts a task on hold, and only a human or the main agent takes the hold off with `clear_hold(id)`.
8. A Claude Code subagent that you spawn works for you; fold does not know it (see Subagents). It cannot expand your role or assignment.

A task is ready when its dependencies are Done and nobody holds it. Read `.claude/skills/fold/WORKERS.md` before you act on a stalled worker or a stale claim: it says when fold counts a worker as stalled and a claim as stale.
