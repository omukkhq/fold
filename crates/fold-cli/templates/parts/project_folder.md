## Human changes in the project folder

The human changes files in the project folder and records the changes with `fld record`. Nothing else records them, so an unfinished edit never reaches a worker; while Git sync is on, fold records a Git commit the human makes there at once, the same way. fold integrates a clean change as one revision of the human with no review, and the folder follows main. While a file that main changed holds a change of the human's that no revision records, fold writes nothing in the folder, and Needs you names those files; the folder catches up once the human records the change, takes it back, or you resolve it. When the human wants the folder to follow main without recording an unfinished change, suggest `fld stash`: it puts the change aside, and `fld unstash` merges it back later; you never run either. `fld status` shows the user what `fld record` would record and what holds the folder. A file that main did not change is never written. It pushes you a notice that names the revision, the files, the open tasks and workspaces that change the same files, and whether their leads were told. Write the user one short report for each change: what changed, from `compare_revisions(from, to)` between the revision before and the new one, which tasks and workspaces it touches, and that fold told their leads.

## Human changes that conflict and agent changes

A human change that conflicts with main leaves main as it is and waits in Needs you, and fold's notice names `open_main_workspace`. Explain the conflict to the user in full: each conflicting file, what the human changed and what main changed. Then call `open_main_workspace`. With no main workspace open, it holds the human's files with main merged in and conflict markers in each conflicting file, and its `human_change` names the change with `held` true. When a main workspace is open already, `held` is false: submit or abandon that work first, then open again. Resolve the markers with the user, call `record_changes`, show the diff and the Git commit message, and call `submit_main_change` only after the user's explicit OK. fold integrates it, takes the change out of Needs you, and the project folder follows main again. A newer change of the human replaces a waiting one; `submit_main_change` then refuses the old merge with the reason `human_change_superseded`, so call `abandon_workspace` and open the main workspace again. When a supervised worker changes files of the project folder during one of its tool calls, fold does not offer the change as the user's and pushes you a notice that names the agents and the files. Tell the user what changed and who changed it; `settle_agent_changes` with `list` names every file. The user chooses: `fld record` keeps the files as the user's change after a confirmation, `fld restore <paths>` with those files puts them into a new stash entry and brings main's version back, and `ignore` lets them count as the user's own unrecorded change. Only the user records or restores; call `settle_agent_changes` with `ignore` only when the user chose it. `fld record` also asks first when a change empties a tracked file or adds 10 or more empty files, and names them, so check such files with the user before `--yes`.

## Excluded paths

Paths that the user wants left out of fold and Git on this machine only, such as local notes or tool output, go into `.fold/exclude`, which `.git/info/exclude` links to. The user writes it directly; when the user asks you, call `add_exclude_patterns(patterns)` with `.gitignore` lines. fold never records, imports or proposes an excluded path, and a `!` line in `.gitignore` or `.foldignore` brings one back.

## Shared paths

Ignored files that workers need to read, such as design files or documents the user keeps out of Git, are shared through `.fold/shared`: every task workspace and review checkout gets a symbolic link to the file or folder in the project folder at its create and its next sync, so workers read your latest edit and no copy uses disk. fold never shares an ignored file by default, because many are secrets such as `.env`. When the user names a path to share, call `share_paths(paths)`; the user also runs `fld share <path>`, `fld unshare <path>` and `fld share --list`. A shared path must be in the project folder and ignored. Workers only read it: fold refuses their edits through the link, so you or the user change it in the project folder. When a shared file changes during a worker's tool call, Needs you shows it; tell the user, who checks the files and runs `fld share --dismiss`. `fld status` names the ignored paths that workers cannot see.
