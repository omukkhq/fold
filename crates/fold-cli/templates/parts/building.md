## Building a task

A task worker builds one task at a time, and so does the main agent for a task of `main`.

1. Read assigned tasks with `get_task(id)`, including kind, scope, dependencies and acceptance criteria. A task worker works only on its assignments.
2. Leads hand out the work. A task worker that fold started already holds the claim on each of its tasks: its area lead's `start_worker` gave it. It never claims, and `claim_task` and `takeover_claim` refuse it with `worker_claim_denied`; it tells its lead about other work. Only the lead of the task's area and the main agent, when the user tells it to, call `claim_task(id)`; the main agent claims a task of `main` without a further word; a session without a fold role and the review lead get `orchestrator_required`. On `already_claimed`, read the holder and tell your lead; do not take unrelated work.
3. Call `get_workspace(ws or task)`, or read the workspace that `claim_task` returned when you claimed the task yourself, and reuse it: a task taken over from another worker already has one. Call `create_workspace(task)` only when none exists. Work only there under `.fold/ws/` and inspect changes with `get_workspace_changes(ws)`.
4. Read the repository's `AGENTS.md` or `CLAUDE.md`. When the project has `fold-checks.toml`, call `run_checks(task)`: fold runs its setup and the proposal checks whose `files` pattern matches your change in your workspace, and returns at once. The result comes as a message from fold, a failure with the check names and the end of the log. Wait for it with `wait_for_events` and the type `checks.finished` on the task, and read every result with `get_check_run(run)`. A check that changes recorded files fails the run, so put what a check writes in `.gitignore`. Run the other acceptance and required repository checks in the workspace, then inspect the final changed files. Resolve failed required checks or report the blocker before proposing. Tick each plain checklist step of your own task with `update_checklist_item(id, done)` when the step is done and checked, before the proposal or report.
5. Save your progress with `record_checkpoint(ws, label?)`. Read the checkpoints with `list_checkpoints(ws)`, and go back with `restore_checkpoint(ck)`. If `restore_checkpoint` fails with `unrecorded_changes`, call it again: the new call records your latest edits in its safety checkpoint. fold also records checkpoints by itself after a quiet time.
6. When the task is finished, call `record_changes(ws, message)`. The message says what changed and why.
7. If main moved, call `sync_workspace(ws)`. Resolve each conflict in the workspace files: remove the conflict markers, and remove each `<path>.fold-main` file after you merge it. Then record again. `record_changes` refuses with `unresolved_conflicts` while a conflict stays. Read `get_repository_state`, `get_revision(r)` and `compare_revisions(from, to, path?)` to see what changed on main.
8. Open the proposal with `create_proposal(task, title, intent, evidence?)`. The title becomes the Git commit subject: a short imperative of at most 72 characters. The intent explains how the change works in the code, so a human understands and judges it without reading every line, and the reviewer checks every hunk against it. It always has a `summary` (2 to 4 sentences, at most 1200 characters: the flow, the states and the rules in the terms of the code, such as functions, tables and routes, not the task's words) and `parts` (1 to 12): each part has a short `name`, what that part of the code `does` (at most 800 characters) and its `files`. Every file the version changes against its base belongs to exactly one part, generated files too (for example a part "Generated API client"); a small fix has one part. Add the other sections only when they apply: `contracts` with only the kinds the change touches (`routes`, `database`, `rights`, `config`, `errors`, `events`, `commands`), each a list of one-line entries, so every migration, route, right, config key, error code, event or command the diff adds or changes is named; `decisions` (the choices and why, and open questions with the message id that asks them); `not_changed` (what a reader may think it touches but it does not). The summary, the parts and the contracts become the body of the Git commit. `invalid_intent` names the field and the reason in its details; `part_files_uncovered` lists the changed files no part names in `details.uncovered`, and `part_file_outside_diff` the named files the version does not change in `details.outside`. Evidence gives actual check commands, results and any checks that could not run. The first version is `v1`; proposal creation snapshots and records the workspace's current files. When `fold-checks.toml` has proposal checks for the change and no passed `run_checks` of the same files stands, the call answers with `checks` `running` and a run id instead: fold runs the checks and opens the proposal only when they pass. Wait for `checks.finished` as in step 4; on a failure, fix the work and call `create_proposal` again. `update_proposal` waits for the checks in the same way. A version that adds, changes or removes `fold-checks.toml` gets the human review mark, so a human approves every change of the checks. A human edit, `fld record` and the main agent's `submit_main_change` run no proposal checks. The integration checks run only when a proposal integrates, a human-edited version included, so `fld record` and `submit_main_change` run none.
9. Read the review with `get_review_comments(id, version?)`. Fix the points in the workspace, record again, and call `update_proposal(id, intent, evidence?)` with the intent of the whole change as it stands now, its parts covering every file the new version changes. This opens `v2`, which starts without approvals. On a task with the human review mark, the human reviewer may also edit a file of your version. fold adds that edit as the next version under the human's name and sends you a push. The reviewer may also fix your version itself: fold adds the fix as the next version under the reviewer's name and sends you a push. After either, call `sync_workspace(ws)` before you work in the workspace again: it writes that version into the files, and until then `record_changes` and `update_proposal` fail with `workspace_write_unfinished`. Continue from that version and keep its changes.
10. Call `close_proposal(id, reason)` to withdraw a proposal. `abandon_workspace(ws, reason)` refuses with `invalid_request` and the reason `proposal_open` while a proposal for the task is open: call `close_proposal` first.
11. Call `release_task(id)` when you cannot finish the task, and tell your lead. The lead of the task's area takes a task whose claim is stale with `takeover_claim(id)`, or starts a new task worker for it, which takes the stale claim over. `takeover_claim` fails with `claim_not_stale` while the lease is valid.
