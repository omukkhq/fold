## Review scope

The change of `get_proposal_diff(id, since)` leaves out what main gained when the worker synced, and lists `earlier` (the earlier version's own change size), `new_files` (files the earlier version did not change), `base_moved` and `base_conflicts` (files where the worker merged main by hand). From these facts fold suggests the review scope in `suggested_scope`, with the rules behind it in `scope_rules`: a full review when the delta changes a file in `new_files` (`new_files`), has more added and removed lines than half of `earlier` (`large_delta`), has `base_conflicts` (`base_conflicts`), or the version is `v3` or later (`v3_or_later`); otherwise a review of the change. The review lead decides the scope when it assigns the review: it accepts the suggestion by passing nothing, or chooses the other scope with a reason in `scopes` of `start_worker`; the main agent chooses one for its own review in `scope` and `reason` of `claim_review` or `scopes` of `create_review_batch`. It chooses a full review for what fold cannot see, such as a change to a public API, a schema, a migration, or security or permission code, and a change review when the reach is small, such as a `v3` that only changes strings. For a version that comes after the assignment, such as a reviewer's own fix version, or to choose again, the review lead or the main agent calls `set_review_scope(id, version, scope, reason)`; the newest choice for a version applies. `get_proposal` shows the choice in `review_scope` under `chosen`; without one the review follows `suggested_scope`. A reviewer follows the scope it gets, and tells the review lead when a change review meets what it does not cover. A full review reads the whole version; a change review reads the delta and the callers and tests of the code it changes, to confirm the fixes. Another reviewer's verdict does not prove unchanged code correct. fold stores the scope with each review, and `get_proposal` shows it in each review's `scope` with the rules; do not write it in the review body.

## Integration

fold integrates a ready proposal by itself when the project integrates automatically, which is the default: a reviewer, the main agent or a human approved it, nothing asks for changes, a marked task has an approval by a human that the mark accepts, and every prerequisite task is Done. In a project that does not integrate automatically, call `integrate_proposal(id, expected_version?)` when the proposal is ready. Pass the version you reviewed as `expected_version`: if a newer version exists, the call fails with `stale_version`. fold checks the approvals, the human review mark and the prerequisite tasks before it moves main. The approved members of a submitted review batch integrate together: once every member has its final state for the batch (approved, or out because changes were requested, it was rejected, closed or removed, or it waits for a human or for a member that is out), fold merges the approved ones onto main in dependency order, runs the integration checks once on the whole merge, and publishes one revision per member in one step. A member that conflicts goes back to its author alone. When that one check run fails, fold integrates the members one at a time, each with its own run, and only a member whose own run fails goes back. A member that is out integrates later on its own rules. An hour after the batch review, a member that still has no final state is out too. In a project that does not integrate automatically, call `integrate_review_batch(id)` for a ready batch; it refuses a batch with members that have no final state with `invalid_request` and the reason `batch_waiting`. `integrate_proposal` still integrates one member alone.
