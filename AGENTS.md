# AGENTS.md

fold: a local-first platform where independent AI coding agents plan, build, review and integrate software through one daemon. It joins a native version control system (content-addressed objects, workspaces, checkpoints, changesets, three-way merge, atomic integration), a dependency task graph shown as a five-column Kanban board whose status is always calculated, fold-native proposals and review, and persistent agent messaging and events. `crates/` is the Rust workspace: `fold-core` (pure decisions), `fold-vcs` (objects and workspace files), `fold-store` (SQLite), `fold-daemon` (services, live state, HTTP, SSE, MCP) and `fold-cli` (the `fold` binary). `web/` is the browser application: Vite + React, managed by bun, built into the binary. Claude Code sessions connect through `fold mcp`, a stdio adapter to the daemon's Unix socket. The screens are drawn in `~/programming/pencil/fold.pen`, one frame per screen, named by code (`W02`, `W03`, …). This file holds the rules for writing code here.

## General

1. **Never hand back work on a red check.** If rustfmt, clippy, nextest, coverage, tsc, eslint or vitest fails, fix it, even if your change didn't cause it.
2. **Keep the projects apart.** `web/` never reads from `crates/`. The OpenAPI schema is the only contract between the daemon and the web application, and the MCP tool schemas are the only contract with agents.
3. **Always generate files that can be generated by a tool.** Migrations come from `make migration NAME=<name>` (`sqlx migrate add` in `crates/fold-store/migrations/project`; add `DB=registry` for the host registry); the daemon applies both sets when it opens a database, query metadata in `.sqlx/` from `make sqlx-prepare`, the web API types from `make gen-api`, and lockfiles from cargo and bun. Edit a generated file only for a specific change it genuinely needs.
4. **Never hand-edit dependency manifests.** Add, remove or bump a dependency with `cargo add -p <crate>` / `cargo remove -p <crate>` and `bun add` / `bun remove` inside `web/`. Non-dependency config in `Cargo.toml` and `package.json` (lints, profiles, features, scripts) is fine to edit directly.
5. **cargo for Rust, bun for JavaScript, always.** Use `bun install --frozen-lockfile`, `bun run` and `bunx`. Commit `bun.lock`, never `package-lock.json` or `pnpm-lock.yaml`, and never call `npm`, `npx`, `pnpm` or `yarn`.
6. **Ask instead of leaving questions in deliverables.** No TBDs, open questions or "this doesn't match X" in code, docs, Pencil annotations or commit messages.
7. **Comment only what the code can't say.** A comment states a non-obvious, project-specific fact; it never narrates the code. Doc comments explain why something has its shape. No module-level `//!` narration.
   **Describe what is, not what was.** Docs and comments state how the code behaves today. No "no longer", "as before" or "now does X instead of Y"; what changed and why belongs in the commit message.
8. **Never cite planning documents in code or commits.** They change; state the rule or the reason itself.
9. **Don't hard-wrap prose.** One paragraph is one line in Markdown and commit messages. Code width is the formatter's job.
10. **When the code and a settled product decision disagree, stop and ask.** Never resolve the conflict silently in either direction.
11. **No mock or hard-coded demo data in app code.** An empty project renders empty states. Demo data comes from `make seed-dev`, which builds a throwaway project through the real commands.
12. **Read Pencil designs through the Pencil MCP only.** Never cat, grep or parse a `.pen` file.
13. **Write all communication with the user in ASD-STE100 Simplified Technical English.** This covers every message to the user: answers, questions, plans, summaries and reports. Use only approved words with their approved meanings, plus technical names and technical verbs. Write sentences of 20 words or fewer in instructions and 25 or fewer in descriptions, with no more than six sentences in a paragraph. Use the active voice. The rule does not change code, commands, paths, identifiers, docs or commit messages.

## Commands

**The Makefile is the interface.** `make help` lists every target; prefer a target over the raw command.

```bash
make setup                 # toolchain components, cargo tools, bun install, git hooks (once per clone)
make dev                   # daemon with reload on :7420 plus the Vite dev server on :5173
make dev-daemon            # daemon only (also dev-web)
make gen-api               # regenerate web/src/api/schema.d.ts from `fold openapi` (no daemon needed)
make migration NAME=<name> # new project migration; DB=registry for the host registry. The daemon applies migrations itself.
make sqlx-prepare          # refresh .sqlx/ query metadata after changing a query
make fmt                   # cargo fmt, eslint --fix, prettier --write
make check                 # fmt check, clippy, nextest, coverage floors, tsc, eslint, vitest, web build, stale-client check; run before declaring work done
make check-rust            # the Rust half of check
make check-web             # the web half of check
make acceptance            # the acceptance tests only
make seed-dev              # development only: a throwaway project with agents, tasks, workspaces and a proposal
make release               # web build, then fold for x86_64 and aarch64 Linux into dist/
make clean                 # delete build output and dev projects
```

Before declaring Rust work done, run `make check-rust`; for web work, `make check-web`. A change to an HTTP route also runs `make gen-api` and commits the regenerated types. A change to a query also runs `make sqlx-prepare`.

## Rust

1. **No `unsafe` without a `// SAFETY:` comment** that explains why the invariants hold. The workspace lints warn on `unsafe_code` and `clippy::undocumented_unsafe_blocks` is denied.
2. **No `unwrap`, `expect`, `panic!`, `todo!`, `dbg!` or `println!` outside tests.** clippy denies them. `fold-cli` alone writes to stdout, through its output helpers.
3. **Suppress a lint only with `#[expect(lint, reason = "...")]`.** Never `#[allow]`, never a crate-wide relaxation.
8. **Pin the toolchain and version once.** `rust-toolchain.toml` pins the channel with the `minimal` profile, `rustfmt` and `clippy`; move it in its own change with every check green. The workspace uses `resolver = "3"` and edition 2024. Every crate takes `version.workspace = true`, so one number versions the binary. The release profile sets `lto = true` and `codegen-units = 1`; a `ci` profile inherits it with `lto = false` so checks run fast.
4. **Library errors are `thiserror` enums; `FoldError` carries a stable `code` string.** Never change a shipped code. `anyhow` only in `fold-cli`'s `main`.
5. **Blocking work never runs on the async runtime.** File I/O on workspaces, hashing, compression and merging go through `spawn_blocking`. Never hold a `std::sync::Mutex` guard across an `.await`.
6. **Time and randomness are inputs.** `fold-core` takes `now` as an argument. `fold-core` defines the `Clock` trait and `ManualClock` for tests; `fold-daemon` provides `SystemClock`. Services and jobs read time only through a `Clock`. Timestamps are UTC milliseconds in the `Timestamp` newtype; never a local time.
7. **Public ids are the prefixed numbers** (`T-12`, `P-3`, `C-40`, `r17`, `ws-9`, `ck-88`, `m-210`), parsed and printed by the id types in `fold-core`. A SQLite row id never leaves the daemon.

## Database

1. **One SQLite file per project, WAL, `synchronous=FULL`, `foreign_keys=ON`.** All writes go through the project's single writer (`Store::write`); reads use the read pool.
2. **Migrations are forward-only.** Never edit a migration that has been applied anywhere; add a new one.
3. **Append-only tables get triggers that refuse `UPDATE` and `DELETE`** in the migration that creates them: events, revisions, changesets, proposal versions, reviews, review comments, integrations, completions, messages.
4. **Let the database hold the invariants it can.** One unreleased implementation claim per task, one unreleased review claim per proposal, one active task workspace per task, one open proposal per task, unique `(proposal, version)` versions, no self-dependency, one id number per kind per project: each is a constraint, not only a service check.
5. **A column used to filter, join, constrain or decide is a real column,** never a key inside a JSON column.
6. **`tasks.status` and `tasks.blocked` are caches.** Only `recompute` writes them, inside the transaction that changed their inputs.

## Layout

1. **Split each layer by domain, never by entity.** Domains are `projects`, `agents`, `tasks`, `workspaces`, `reviews`, `messages`, `events`. A domain is one module until it grows, then a directory whose `mod.rs` exposes the same names. A domain module is created when its first code lands, never as an empty placeholder.
2. **Keep `fold-core` pure.** It does no I/O: no files, no SQLite, no tokio, no clock, no environment. The DAG, status, readiness, the container rule, the policy gates, diff3, tree merge and the object encodings live there, so every decision is replayable from stored inputs.
3. **Crates depend toward `fold-core`.** `fold-vcs` and `fold-store` depend only on `fold-core`; nothing below `fold-daemon` knows about HTTP, MCP or the event bus.
4. **Only commands change state.** A mutating service function takes the acting `Actor`, checks it with `fold_core::policy`, and runs one write transaction. There is no generic setter for status, claims, heads or proposal versions.
5. **Events go in the same transaction as the change; publish after commit.** Append with `events::append(tx, …)` inside the write; send to the bus only once the transaction has committed. A live `workspace.changed` event is the only event that is not stored.
6. **Keep transports thin.** MCP tools (`mcp/<domain>.rs`) and HTTP handlers (`http/<domain>.rs`) parse input, call the same service function, and map the result. No rule lives in a transport.
7. **Every HTTP route declares its response schema and error responses with utoipa;** every MCP tool input derives `JsonSchema` with a description on each field. The web types and the agents' view are generated from them.
8. **MCP results are compact.** Public ids, no row dumps, and the footer from `mcp::footer` on every result. Errors carry `code`, message and a hint naming the next tool.

## Invariants

1. **Objects before references.** An object is written, flushed and renamed into place before any row or object refers to it. A hash never changes for the same content.
2. **The main head moves only through the integration procedure,** under the project's integration mutex, by compare-and-swap. A published revision is never partial.
3. **Done means a completion record,** written in the same transaction as the integration (or by the container rule in `recompute`). A failed integration never completes a task.
4. **Proposal versions never change.** Approvals belong to the version they reviewed; a new version starts unapproved.
5. **fold writes into a workspace only on create, sync and restore,** and never copies unrecorded changes between workspaces. Nothing deletes a workspace directory except `fold gc` after the retention period.
6. **Messages never change task state,** never stand in for a dependency and never stand in for a claim.
7. **Every path from an agent or a tree is checked** to be relative, normalised and inside its workspace before it is read or written. Symlinks are recorded, never followed.
8. **Log ids, never content.** No file content, diff text, message body, review body or token in a log line or an error detail.
9. **Off loopback, every `/api` route needs the session cookie.** The static web files load without it so the sign-in screen can open. Tokens are stored hashed and compared in constant time. The Unix socket is mode `0600` and never exposed on the network.

## Web

1. **Keep the application static.** Vite + React with no SSR; routing with TanStack Router, server state with TanStack Query, forms with react-hook-form and zod.
2. **Use the semantic tokens in `web/src/styles/tokens.css`, never raw colours.** Their names match the variables in `fold.pen`; type, spacing and radii come from the tokens too.
3. **Build on Radix primitives** for menus, dialogs, popovers, tabs and tooltips. Don't hand-roll focus management.
4. **Use Lucide icons** (`lucide-react`).
5. **Call the API only through `web/src/api/client.ts`.** Type data with the generated schema types, never a hand-written copy. Branch on the error `code`, never the message.
6. **Live data comes from the event stream.** Apply events to the Query cache through `web/src/live/`; never poll a screen that the stream covers.
7. **The board is read-only.** No drag and drop, no status control; cards move only because the daemon's state changed.
8. **Show a pending state, never optimistic success,** for every human write.
9. **Match the Pencil frame for the screen you build.** Open it through the Pencil MCP by its code, and take loading, empty and error states from their frames or the shared patterns in `W00`.
10. **Load every font and asset from the bundle.** Nothing comes from a CDN.
11. **TypeScript is strict.** No `any`, no `@ts-ignore`, no `as unknown as`. Keep components thin and put their decisions in tested `.ts` modules.

## Tests

1. **Test `fold-core` without infrastructure.** It is pure by design; a test that needs a file or a database there means the code is in the wrong crate. Use proptest for merge, DAG and status properties.
2. **Service tests use the `TestProject` fixture:** a temporary project with a real SQLite file and object store. Never mock SQLite or the file system.
3. **Call MCP tools through an in-process rmcp client and HTTP routes through `tower::ServiceExt::oneshot`,** not a live port.
4. **Wait for watcher and event effects with a timeout, never a fixed sleep.**
5. **Every product acceptance scenario has its own `acceptance_<n>_*` test** with three MCP clients as frontend, backend and review. Keep them passing.
6. **Crash safety is tested with failpoints** (the `failpoints` feature): stop inside a command and check that a restarted daemon shows all of the change or none of it.
7. **Hold the Rust workspace to 85% line coverage and `web/src/**/*.ts` to 85% line and 85% branch coverage, each on its own.** `.tsx` files aren't measured; their logic belongs in `.ts` modules. Raise a number with tests of real behaviour, never by excluding reachable code.

## Git

1. **Never commit with `--no-verify`.** The hooks in `.githooks/` run `make fmt` checks, clippy and the fast tests; fix what they reject, re-stage and commit again.
2. **Write commit messages for the person reading the history:** what changed and why it matters, not the mechanics visible in the diff.
3. **No trailing signature:** no `Co-Authored-By`, `Generated with …`, or any attribution footer.
4. **Commit to the current branch.** Don't create a separate branch to hold the work unless asked.
